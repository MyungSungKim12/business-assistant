# N1030-08 고객 메시지 초안 설계

날짜: 2026-11-03 · 기존 승인 설계: `docs/superpowers/specs/2026-10-30-product-completion.md` 항목 8

## 의도

매장 직원이 예약 확인/변경이나 방문 후 안내 메시지를 준비하고, 대상·동의 제외 사유를 확인한 뒤 발송 대기 이력으로 보존한다. 공급자 계정/자격 증명이 없는 현 상태에서는 전송·전달 성공을 표시하지 않는다.

## 범위

- 조직별 메시지 템플릿의 등록/수정/버전 보존과 허용 변수 검증
- 고객 ID 기반 발송 미리보기: 고객 상태, 연락처, 현재 마케팅 동의를 DB에서 재확인하고 제외 사유를 반환
- 단일 작업의 멱등성, 스케줄 시각, 조직별 outbox 내역, 취소와 제한된 재시도
- 실제 전송 API 경계와 공급자 미설정 안내. 공급자 설정이 없다면 outbox는 대기 상태이며 성공/전달로 바꾸지 않는다.
- CRM 권한/조직 확인, RLS RPC-only 데이터 접근

## 명시적 제외

알림톡/SMS 업체 선택·실 계정 연결, 실제 메시지 발송, 전달 webhook, 답장 처리·자동 후속 업무, 캠페인 전환 성과, 일정 변경 자동 편성, 고객에게 테스트 메시지 발송. 외부 공급자 선정/비밀값이 아직 제공되지 않았다.

## 구현 선택

1. 브라우저/PC에서 공급자 API 직접 호출: 비밀값 노출과 승인 동선 우회 위험으로 제외.
2. 공급자 모듈이 없는데 성공을 흉내내는 mock: 실데이터 오인을 일으켜 제외.
3. 기존 Node API가 Supabase 권한 RPC를 통해 템플릿/outbox를 관리하고, 전송 어댑터는 fail-closed 미설정으로 둔다: 기존 아키텍처에 맞고 실제 연동 전까지 정직한 상태를 유지하므로 선택.

## 계약/보안

- 광고 목적 메시지는 enqueue 시점 및 실제 worker dispatch 직전에 최신 `marketing_consent=true`를 확인해야 한다. 이번 범위에서는 DB enqueue 시점을 구현하고 실제 worker dispatch 전 검사는 후속 공급자 작업의 필수 계약으로 기록한다.
- 수신 전화번호/본문을 API·감사 로그에 출력하지 않는다. outbox에는 고객 ID와 템플릿 버전/목적/일정만 보존한다.
- 최대 미리보기·enqueue 200명, 템플릿 본문 4,000자, 3회 이하 재시도. 클라이언트가 전달하는 조직/수신 자격·상태는 믿지 않는다.
- 멱등 재전송은 동일 operation ID를 사용하며 수신자별 중복 row를 만들지 않는다.

## 진행자의 결정

기존 `marketing_consent`가 고객 프로필의 현재 동의 상태임을 보존하고, 동의의 변경 이력/증빙 모델은 확대하지 않는다. 이번 구현은 P0 운영 기반이며 실제 발송 공급자 연결 전에는 발송 대기 기능으로 표시한다.
