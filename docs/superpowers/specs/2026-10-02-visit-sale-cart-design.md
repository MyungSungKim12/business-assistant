# SALE-001 방문별 결제 장바구니 설계

작성일: 2026-10-02  
상태: 사용자 승인 설계를 문서화한 구현 전 명세  
관련 기능: SALE-001, TRT-003, 향후 APT-003·SALE-002  

## 목적

접수 직원이 한 고객의 방문에서 발생한 시술 청구 초안을 한곳에 모아 실제 청구 항목과 담당자를 검토할 수 있게 한다. 장바구니는 결제 전 작업 공간이며 그 자체로 수납, 확정 매출, 재고 차감, 회원권 차감 또는 직원 실적을 만들지 않는다.

성공 기준은 다음과 같다.

- 시술에서 전달한 미수납 초안을 같은 고객의 열린 방문 장바구니에 한 번만 담는다.
- 직원은 항목, 수량, 단가, 담당자 스냅샷과 합계를 확인할 수 있다.
- 네트워크 실패, 메뉴 이동, 고객 전환 및 동시 수정에서도 입력과 서버 상태를 구분해 복구할 수 있다.
- 다른 조직이나 권한 없는 사용자가 장바구니를 읽거나 변경할 수 없다.
- 아직 구현되지 않은 제품·회원권 마스터를 임의 데이터로 대신하지 않는다.

## 선택한 접근

기존 `treatment_sale_drafts`를 폐기하거나 직접 수정하지 않고, 별도의 방문과 장바구니 계층을 추가한다. 시술 결제 초안은 불변 원천 스냅샷으로 유지하고 장바구니 항목이 해당 초안을 참조한다.

이 구조는 기존 초안의 감사 의미를 보존하고, 향후 제품·회원권·예약 원천을 같은 장바구니에 연결할 수 있다. 기존 재무 거래인 `finance_transactions`와도 분리하므로 SALE-002 구현 전 장바구니 금액이 실제 수입 합계에 섞이지 않는다.

## 범위

### 이번 구현에 포함

1. 고객별 열린 방문 생성·조회·취소
2. 방문과 1:1인 초안 장바구니
3. 기존 시술 결제 초안을 장바구니 항목으로 가져오기
4. 장바구니 항목 수량·단가·담당자 표시와 서버 계산 합계
5. 항목 제거, 취소한 항목 복원, 낙관적 버전 충돌 처리
6. 요청 재전송 시 중복 생성되지 않는 작업 ID
7. 매출·지출 메뉴의 3열 장바구니 작업 화면
8. 작성 중 입력 보호, 부분 로딩 실패, 재시도 및 권한 상태

### 후속 기능으로 유지

- SALE-002 실제 현금·카드·이체·지갑 수납
- SALE-003 환불과 역분개
- SALE-004 할인·쿠폰·포인트 계산
- INV 제품 마스터와 실제 재고 차감
- WAL 회원권 마스터와 회차 차감
- TEAM 직원 마스터를 사용한 담당자 재배정과 수당
- APT 예약에서 방문 자동 생성 및 체크인
- 영수증 발행, 결제 단말기, 일 마감

제품·회원권 원천이 준비되기 전에는 해당 항목 종류를 화면에 가짜 선택지로 노출하지 않는다. 데이터 계약은 향후 항목 종류를 추가할 수 있게 설계하지만, 이번 서버는 `treatment_draft`만 생성 가능하게 검사한다.

## 데이터 모델

새 migration은 기존 001~023 이후 번호를 사용한다. 실제 파일 번호는 구현 시 저장소의 최신 번호를 다시 확인한다.

### `customer_visits`

| 필드 | 규칙 |
| --- | --- |
| id | UUID 기본 키. 예약 없는 방문도 서버가 생성한다. |
| organization_id, customer_id | 필수. 고객이 같은 조직에 속하는지 서버와 DB에서 확인한다. |
| appointment_id | 예약 기능 연결 전에는 null. 향후 조직이 일치하는 예약만 허용한다. |
| status | `open`, `checkout_ready`, `closed`, `canceled`. 이번 범위에서는 open/canceled만 변경한다. |
| opened_at, closed_at | 시간대 포함. closed는 SALE-002 확정 후에만 사용한다. |
| version | 1부터 증가하는 낙관적 잠금 버전. |
| created_by, updated_by, created_at, updated_at | 감사 주체와 시각. |

같은 고객에게 열린 방문이 여러 개 필요할 수 있으므로 고객별 단일 open 제약은 두지 않는다. UI는 열린 방문의 시각과 ID를 보여 사용자가 명시적으로 선택하게 한다.

### `sale_carts`

| 필드 | 규칙 |
| --- | --- |
| id, organization_id, visit_id, customer_id | 방문과 1:1. 조직·고객 범위가 모두 일치해야 한다. |
| status | `draft`, `ready`, `void`. 이번 범위에서 ready는 검토 완료 표시이며 수납 완료가 아니다. |
| version | 모든 항목 변경 때 증가한다. 클라이언트는 예상 버전을 보낸다. |
| subtotal, discount_total, total_amount | DB RPC가 Decimal 두 자리로 계산한다. 이번 범위의 discount는 0이다. |
| created_by, updated_by, created_at, updated_at | 감사 필드. |

클라이언트가 합계를 직접 확정하지 않는다. 응답의 합계만 화면과 후속 SALE-002 입력으로 사용한다.

### `sale_cart_lines`

| 필드 | 규칙 |
| --- | --- |
| id, cart_id, organization_id | 장바구니 범위. |
| source_type | 이번 범위는 `treatment_draft`. 향후 `product`, `membership`을 추가한다. |
| source_id | `treatment_sale_drafts.id`. 같은 원천은 활성 항목 한 곳에만 존재한다. |
| description_snapshot | 원천 전달 당시의 사람이 읽을 수 있는 항목명. |
| quantity, unit_price, line_total | quantity는 양수, 금액은 0 이상 Decimal 두 자리. line_total은 서버 계산값. |
| staff_id, staff_name_snapshot | 직원 ID가 원천에 있으면 보존하고, 현재 초안처럼 이름만 있으면 스냅샷만 기록한다. |
| source_snapshot | 원천 초안 ID, 고객, 시술 버전, 동의 상태 등 재현에 필요한 JSON. |
| status | `active`, `removed`. 삭제하지 않고 제거 사유와 주체를 기록한다. |
| created_by, removed_by, created_at, removed_at | 감사 필드. |

활성 항목에 대해 `(organization_id, source_type, source_id)` 부분 고유 인덱스를 둔다. 제거 후 다른 열린 장바구니로 옮길 때는 새 항목을 만들고 이전 제거 이력을 보존한다.

### `sale_cart_operations`

모든 변경 RPC는 `operation_id`, 요청 fingerprint, 결과 스냅샷을 기록한다. 같은 ID와 같은 요청은 기존 결과를 돌려주며, 같은 ID에 다른 요청은 충돌로 거부한다. 이 테이블은 조직, 사용자, 장바구니 범위로 RLS를 적용하고 일반 클라이언트의 직접 쓰기를 금지한다.

## 서버 계약

기본 경로는 `/api/v1/organizations/{organization_id}`다.

| 메서드와 경로 | 동작 |
| --- | --- |
| `GET /visits?customer_id=&status=` | 조직 범위 방문 목록 |
| `POST /customers/{customer_id}/visits` | 예약 없는 열린 방문과 빈 장바구니를 원자 생성 |
| `GET /visits/{visit_id}/sale-cart` | 방문·장바구니·활성/제거 항목·합계 조회 |
| `POST /visits/{visit_id}/sale-cart/lines/treatment-draft` | 시술 결제 초안을 검증해 항목으로 추가 |
| `PATCH /visits/{visit_id}/sale-cart/lines/{line_id}` | 수량·검토 단가·담당자 스냅샷 변경 |
| `POST /visits/{visit_id}/sale-cart/lines/{line_id}/remove` | 사유와 함께 항목 제거 |
| `POST /visits/{visit_id}/sale-cart/lines/{line_id}/restore` | 원천 중복을 다시 검사한 뒤 복원 |
| `POST /visits/{visit_id}/sale-cart/review` | 최신 버전과 원천 유효성을 확인해 ready/draft 전환 |
| `POST /visits/{visit_id}/cancel` | 활성 항목이 없는 방문만 취소하거나 명시적 항목 정리 후 취소 |

모든 변경 요청은 `operation_id`와 `expected_version`을 요구한다. 응답에는 최신 version, 합계, 항목 목록, warnings를 포함한다.

### 권한

- 조회: `crm.basic`과 `finance.basic`, 조직 구성원
- 생성·변경·취소: 두 기능 권한과 owner/admin 역할
- 시술 초안 가져오기: 시술 초안의 조직·고객 일치와 현재 사용 가능 상태 확인
- 장바구니 조회는 `document.template` 권한을 요구하지 않는다. 연결된 시술 초안의 동의 스냅샷은 이미 불변 값이므로 그대로 표시한다.
- RLS와 security-definer RPC 모두 `auth.uid()`, 조직 구성원, 관리자 역할을 독립적으로 검사한다.

### 오류 의미

| 상태 | 의미와 UI 처리 |
| --- | --- |
| 400/422 | 형식, 금액, 수량, 상태 전이가 잘못됨. 입력을 유지하고 필드 오류 표시. |
| 401/403 | 로그인·조직·역할·기능 권한 부족. 편집을 중지하고 읽기 가능 여부를 다시 확인. |
| 404 | 고객, 방문, 장바구니, 원천 초안 또는 항목이 해당 조직 범위에 없음. |
| 409 | 예상 버전 불일치, 원천 중복, 같은 operation_id의 다른 요청. 최신 상태를 비교하도록 안내. |
| 503 | 저장소 장애. 결과가 불명확할 수 있으므로 같은 operation_id로 재시도. |

예상 버전이 틀린 요청은 조용히 덮어쓰지 않는다. 재시도 가능한 통신 실패에서는 클라이언트가 payload와 operation_id를 그대로 보관한다.

## 데스크톱 화면

매출·지출 화면 상단의 `시술 결제 초안` 진입점을 `결제 장바구니`로 확장한다. 기존 재무 거래 조회는 유지하며 장바구니는 별도 대화상자 또는 전체 작업 화면으로 연다.

### 3열 구성

1. 왼쪽: 고객 검색, 열린 방문, `새 방문 시작`, 아직 장바구니에 담기지 않은 시술 초안
2. 가운데: 선택 방문의 활성 항목, 제거 항목 접기, 수량·단가·담당자와 원천 상태
3. 오른쪽: 소계, 할인 0원, 청구 예정 합계, 경고, 검토 완료 버튼

각 열은 로딩, 빈 상태, 권한 없음, 일부 실패, 전체 실패를 구분한다. 목록 하나가 실패해도 이미 불러온 방문이나 장바구니를 지우지 않는다.

### 입력 보호

- 다른 고객·방문·메뉴로 이동하거나 창을 닫을 때 변경된 필드가 있으면 버리기/계속 작성 선택을 제공한다.
- 저장 실패 시 입력, operation_id, expected_version을 유지한다.
- 409 응답은 로컬 수정과 서버 최신 값을 함께 보여주고 사용자가 새 버전에 다시 적용하도록 한다.
- 처리 중에는 중복 버튼 입력을 막고, 결과가 불명확하면 동일 요청 재시도만 제공한다.
- 검토 완료 후 원천이나 항목을 바꾸면 다시 draft로 전환하고 재검토를 요구한다.

## 원자성과 감사

- 방문과 빈 장바구니 생성은 한 RPC 트랜잭션이다.
- 항목 추가·수정·제거·복원은 각 한 RPC에서 버전 검사, 원천 검사, 합계 재계산, 작업 영수증 저장까지 끝낸다.
- `treatment_sale_drafts` 원본은 수정하거나 삭제하지 않는다.
- 장바구니 항목의 제거는 물리 삭제하지 않는다.
- 이번 기능은 `finance_transactions`에 쓰지 않는다.
- 다른 조직 ID를 조합한 요청은 존재 여부를 노출하지 않도록 404 또는 권한 정책에 맞는 403으로 정규화한다.

## 테스트와 검증

### DB

- 방문/장바구니 원자 생성과 operation_id 정확 재시도
- 조직·고객 불일치, 다른 조직 접근, 일반 회원 쓰기 거부
- 같은 시술 초안 동시 추가 시 한 요청만 성공
- 오래된 expected_version 쓰기 거부
- 항목 제거·복원 이력과 합계 재계산
- 0원 항목, 소수 두 자리, 음수·과도한 금액·0 수량 거부
- 장바구니 변경이 `finance_transactions`에 영향을 주지 않음

### 서버

- 기능 권한과 owner/admin 쓰기 검사
- 각 저장소 오류의 4xx/503 변환
- 모든 경로의 organization/customer/visit 범위 전달
- 중복 재시도 응답과 충돌 응답

### 데스크톱

- 방문 선택과 부분 실패가 다른 열의 성공 데이터를 보존
- 저장 실패·고객 전환·메뉴 이동·종료 시 입력 보호
- 동일 operation_id 재시도
- 409에서 서버 최신 상태 안내 및 덮어쓰기 방지
- 읽기 전용 회원과 기능 권한 없음 상태
- 1100×720과 1440×920에서 3열 레이아웃, 키보드 이동, 포커스 표시, 긴 한글 잘림 확인

### 완료 판정

코드·DB·API·Qt 테스트와 대표 화면 렌더링이 통과해도 실제 Supabase migration 적용 전에는 `in-progress`를 유지한다. 실제 테스트 조직에서 방문 생성 → 시술 초안 추가 → 재조회 → 항목 변경 → 검토 완료가 확인되고 다른 조직·일반 회원 거부까지 확인한 뒤 실환경 검증 여부를 별도로 기록한다. SALE-001 전체 완료는 제품·회원권 항목까지 실제 마스터와 연결된 후 판단한다.
