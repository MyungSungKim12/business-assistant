# Business Assistant 설계서

- 작성일: 2026-09-14
- 상태: 사용자 검토 대기
- 대상 경로: `D:\ms\business-assistant`

## 1. 목적

Business Assistant는 업종에 관계없이 사용할 수 있는 Windows 중심의 Python 데스크톱 업무 프로그램이다. 초기 제품은 고객·거래처, 일정·할 일, 문서, 매출·지출, 데이터 가져오기, 보고서의 공통 기반을 제공한다. 이후 학원, 미용실, 부동산 등 업종별 모듈을 독립적으로 추가한다.

제품은 구독 상품에 따라 기능을 허용한다. 메뉴를 단순히 숨기는 데 그치지 않고, FastAPI 서버가 모든 보호된 요청에서 사용자의 구독 및 기능 권한을 다시 확인한다.

## 2. 초기 범위

이번 초기 설정에 포함한다.

- Python 3.13 기반 모노레포
- PySide6 데스크톱 앱의 실행 가능한 최소 화면
- FastAPI 서버의 상태 확인 API
- 공통 설정 및 타입 패키지
- 단위 테스트와 기본 품질 검사
- Supabase 연결을 위한 환경변수 예시와 어댑터 경계
- 제품, 아키텍처, 메뉴, 구독, 개발, 구현, Git 문서
- 로컬 Git 저장소와 첫 커밋

이번 초기 설정에는 포함하지 않는다.

- 실제 Supabase 프로젝트 생성 및 자격 증명 연결
- 회원가입·로그인 화면의 완성 구현
- 실제 결제대행사 연동
- 고객관리 등 업무 모듈의 상세 구현
- 배포 서버 및 Windows 설치 파일 제작

초기 구독은 관리자 또는 테스트 코드가 부여하는 방식으로 설계한다. 결제대행사는 이후 별도 인터페이스 뒤에 연결한다.

## 3. 기술 선택

### 3.1 개발 도구

- Python 3.13
- 패키지 및 가상환경 관리: uv
- 린트와 포맷: Ruff
- 타입 검사: mypy
- 테스트: pytest
- 환경설정: Pydantic Settings
- Git 기본 브랜치: `main`

현재 PC의 Python 3.14에 의존하지 않고 uv가 관리하는 Python 3.13을 사용한다. 저장소에는 잠금 파일을 커밋해 모든 개발자가 같은 의존성을 설치하도록 한다.

### 3.2 애플리케이션

- 데스크톱 UI: PySide6
- API 서버: FastAPI + Uvicorn
- 데이터 계층: SQLAlchemy 2.x + Alembic
- 운영 데이터베이스: Supabase PostgreSQL
- 인증: Supabase Auth
- 파일 저장: Supabase Storage
- API 계약: FastAPI OpenAPI와 Pydantic 모델

## 4. 전체 아키텍처

```text
PySide6 Desktop
  ├─ 로그인/세션 저장
  ├─ 메뉴와 화면
  └─ 로컬 파일·Excel·PDF 처리
          │ HTTPS + access token
          ▼
FastAPI Server
  ├─ JWT 검증
  ├─ 조직/역할/구독 권한 검사
  ├─ 업무 서비스
  ├─ 감사 로그
  └─ DB/Storage 어댑터
          │
          ▼
Supabase
  ├─ Auth
  ├─ PostgreSQL
  └─ Storage
```

데스크톱 앱에는 Supabase 관리자 키나 데이터베이스 접속 문자열을 포함하지 않는다. 앱은 FastAPI의 공개 API만 호출한다. Supabase가 변경되어도 UI와 업무 로직에 미치는 영향을 줄이기 위해 인증, 데이터베이스, 저장소 접근은 각각 인터페이스 뒤에 둔다.

업종별 기능은 `academy.*`, `salon.*`, `realestate.*`처럼 별도 기능 네임스페이스를 사용하며 공통 메뉴 코드를 수정하지 않고 등록할 수 있게 한다.

## 7. 구독 및 기능 권한

권한 판단의 최소 단위는 메뉴 번호가 아닌 문자열 기능 코드다.

```text
dashboard.basic
crm.basic
document.template
automation.custom
ai.summary
```

핵심 개념은 다음과 같다.

- `plan`: 판매되는 구독 상품
- `feature`: 개별 기능 코드
- `plan_feature`: 상품에 포함된 기능
- `subscription`: 조직이 보유한 상품과 유효 기간
- `entitlement`: 현재 시점에 계산된 최종 기능 권한

데스크톱은 로그인 후 권한 목록을 받아 메뉴를 구성한다. 서버는 각 API 요청에서 동일한 기능 코드를 검사하므로 UI 조작만으로 유료 기능을 사용할 수 없다. 권한 응답에는 짧은 만료 시간을 두고, 구독 변경이나 환불 시 서버 판단을 우선한다.

## 8. 데이터 모델 원칙

초기 핵심 엔터티는 다음과 같다.

- `profiles`: Supabase Auth 사용자와 연결된 프로필
- `organizations`: 회사 또는 사업장
- `memberships`: 사용자와 조직의 관계 및 역할
- `plans`: 구독 상품
- `features`: 기능 코드
- `plan_features`: 상품과 기능의 관계
- `subscriptions`: 조직의 구독 상태와 기간
- `device_registrations`: 허용된 PC 등록
- `audit_logs`: 중요한 보안·관리 작업 기록

PostgreSQL 설계 규칙은 다음과 같다.

- 식별자는 lowercase `snake_case`를 사용한다.
- 내부 단일 DB 식별자는 `bigint identity`를 우선한다.
- 외부 노출 식별자는 추측하기 어려운 별도 공개 ID를 사용한다.
- Supabase Auth의 사용자 참조는 `uuid`를 사용한다.
- 시간은 `timestamptz`, 금액은 `numeric`, 상태는 제약조건이 있는 `text`를 사용한다.
- 모든 외래키 열과 테넌트 필터 열에 필요한 인덱스를 둔다.
- 업무 데이터에는 `organization_id`를 포함해 조직별로 분리한다.
- 마이그레이션은 Alembic으로 순서와 이력을 관리한다.

## 9. 보안 설계

- 비밀번호는 애플리케이션 DB에 저장하지 않고 Supabase Auth가 관리한다.
- 데스크톱에는 공개 설정만 포함하며 관리자 키와 DB 비밀번호를 넣지 않는다.
- FastAPI는 Supabase JWT의 서명, 발급자, 대상, 만료를 검증한다.
- 모든 업무 요청은 사용자, 조직 멤버십, 기능 권한을 검사한다.
- 테넌트 테이블에는 RLS를 적용하고 조직 및 사용자 식별 열을 인덱싱한다.
- 일반 API용 DB 역할은 RLS를 우회하지 않는다.
- 관리자 작업은 별도 서비스 클라이언트와 최소 권한 경로로 분리한다.
- 노출 스키마와 권한을 명시적으로 관리하며 공개 역할에 불필요한 권한을 주지 않는다.
- FastAPI는 Supabase의 트랜잭션 풀러를 사용하고 연결 풀 크기를 제한한다.
- 로그인, 구독 변경, 기기 등록, 권한 변경을 감사 로그에 남긴다.

## 10. 주요 데이터 흐름

### 10.1 로그인

1. 데스크톱이 FastAPI 로그인 엔드포인트를 호출한다.
2. FastAPI가 Supabase Auth에 인증을 위임한다.
3. 데스크톱은 짧은 access token과 안전하게 갱신할 수 있는 세션 정보를 받는다.
4. 이후 요청은 HTTPS Authorization 헤더를 사용한다.

### 10.2 메뉴 구성

1. 데스크톱이 현재 사용자의 권한 API를 호출한다.
2. 서버가 조직 멤버십과 활성 구독을 조회한다.
3. 서버가 기능 코드 목록을 계산한다.
4. 데스크톱이 허용된 메뉴를 활성화한다.
5. 실제 기능 API도 같은 기능 코드를 재검사한다.

### 10.3 구독 변경

1. 초기 단계에서는 관리자 명령 또는 테스트 픽스처가 구독을 변경한다.
2. 후속 단계에서 결제 웹훅이 구독 상태를 변경한다.
3. 웹훅은 서명을 확인하고 동일 이벤트의 중복 처리를 방지한다.
4. 변경 결과를 감사 로그에 남기고 기존 권한 캐시를 무효화한다.

## 11. 오류 처리와 관측성

- API 오류는 안정된 오류 코드, 사용자 메시지, 추적 ID를 반환한다.
- 데스크톱은 네트워크 단절과 인증 만료를 구분해서 안내한다.
- 재시도는 조회 등 안전한 요청에만 제한적으로 적용한다.
- 로그에 비밀번호, 토큰, 관리자 키, 민감한 고객 정보를 남기지 않는다.
- 개발 환경은 구조화 로그를 콘솔에 출력한다.
- 향후 오류 추적 서비스는 로깅 인터페이스 뒤에 연결한다.

## 12. 테스트 전략

- 공통 패키지: 기능 코드 및 계약 단위 테스트
- 서버: 상태 확인, 인증 실패, 권한 허용·거부 테스트
- 구독: 만료, 취소, 상품 변경, 중복 이벤트 테스트
- 데이터베이스: 조직 간 데이터 격리와 RLS 정책 테스트
- 데스크톱: 메뉴 권한 매핑과 기본 화면 생성 테스트
- 통합: 데스크톱 API 클라이언트와 FastAPI 테스트 서버 연결
- 품질 게이트: Ruff, mypy, pytest가 모두 통과해야 커밋 완료로 간주

초기 설정은 외부 Supabase 계정 없이 테스트할 수 있도록 가짜 인증·저장소 구현을 사용한다. 실제 Supabase 통합 테스트는 별도의 환경변수가 있을 때만 실행한다.

## 15. 결정 사항 요약

- 모노레포를 사용한다.
- 데스크톱은 PySide6, 서버는 FastAPI를 사용한다.
- 운영 데이터 플랫폼은 Supabase를 우선하되 공급자 경계를 둔다.
- 데스크톱은 DB에 직접 접속하지 않는다.
- 구독은 기능 코드 기반으로 제어하고 서버가 최종 권한을 판단한다.
- 첫 초기화는 골격, 문서, 테스트까지이며 실제 인증과 결제는 후속 단계다.
