# 예약·방문과 개별 시술 연결 계획

> 실행: executing-plans를 적용하여 현재 로컬 변경을 보존한다. 커밋·원격 DB 변경 없이 진행한다.

목표: APT-004 / TRT-001 / TRT-003의 in-progress 범위로 기존 시술 한 건에 예약과 방문을 명시적으로 연결한다. 선행은 063까지의 예약·방문·시술 원장과 기존 화면 진입이다.

구현 선택: 자동 시술/방문/매출 생성 없이 기존 기록을 선택한다. 한 예약·방문에 여러 시술이 가능하다. 준비·진행 중 기록만 사유와 함께 연결/해제하며 완료·중단은 보존한다. 서비스·시술일·금액은 연결만으로 덮어쓰지 않는다.

- [x] SQL 064: nullable appointment_id/visit_id, 고객·조직 복합 FK와 방문/예약 일치 검사. 고객 병합의 트랜잭션 이동을 허용하도록 FK 검사 지연. 새 RPC는 owner/admin·기록 버전·멱등 키·감사 이벤트를 검사하고 고객/예약/방문을 잠금 후 재검증한다. 기존 action 모두 보존한다.
- [x] Node API: 고객별 예약·방문 선택지 GET, 시술 연결 PUT. 조회는 crm.basic, 쓰기는 owner/admin. 입력·응답 scope와 오류를 검증한다. 선택지는 완전 조회하고 실패 시 일부 목록을 반환하지 않는다.
- [x] React: 기존 시술 화면에 연결 창과 연결 ID 표시, 예약 진입 context 전달. 자동 연결 없이 사용자가 저장한다. 실패 입력·operation_id 유지, 충돌·취소·dirty 보호, 늦은 응답 방지.
- [x] 격리 PGlite로 실제 SQL 적용·재적용, 다른 조직/고객·불일치 방문·멱등/충돌·완료 잠금·직접쓰기 차단·고객 이동 검증. 관련 API/React 테스트·타입 검사만 수행한다. 전체 테스트·실제 앱·원격 DB는 제외한다.
- [x] 독립 리뷰와 제품 문서/변경 이력/SQL 적용 안내 갱신. 검증된 범위와 미완료 범위를 구분한다.

기존 작업 기록: API 162개, React 135개, 격리 DB 13개 묶음, 양쪽 타입 검사 통과. 이후 사용자가 SQL 064 실행 완료를 보고했다(원격 독립 확인은 하지 않음). 실제 앱과 실환경 업무 왕복은 미검증이다.
