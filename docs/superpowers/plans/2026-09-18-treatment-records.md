# 시술관리 기록 워크스페이스 실행 계획

**목표:** 고객별 시술 기록을 별도 메뉴에서 등록·조회·수정·복사하고 고객 주의사항을 함께 확인한다.
**기준 문서:** [상담·시술 계획](../../product/menus/04-consultations-treatments.md).
**기술:** 기존 PySide6/HTTP/FastAPI/PostgREST. 스키마 변경·배포·실데이터 수정 없음.

## 기능 범위

TRT-007(신규): 기존 treatment_records 계약에 맞춘 독립 시술 기록 관리. 시술일, 이름, 분류, 담당자, 기록, 예정 금액, 다음 방문 예정일을 저장한다. 예정 금액은 수납/매출 확정이 아니다. 기존 기록 수정은 현재 값 변경이며, 불변 정정 이력은 TRT-002 후속 범위다.

- 좌측 고객 검색/선택과 알레르기·피부 타입 표시.
- 중앙 고객별 이력 표·텍스트/분류/기간 검색과 원본 기록 선택.
- 우측 등록/수정 폼, 이전 기록 복사, 새 기록/입력 취소/저장.
- 비동기 고객/이력 조회 및 저장, 늦은 응답 무시, 중복 저장 클릭 차단.
- 고객·기록 전환/메뉴 이탈/종료의 미저장 입력 보호와 읽기 전용.
- 고객관리에서 선택한 고객의 시술관리로 바로 이동.

## 순서

- [x] 서버 계약 테스트: 입력 검증/인증/구독/역할/조직/없는 기록/장애.
- [x] PATCH API와 저장소 protocol/어댑터 구현. 조직·고객·시술 ID 동시 필터, Decimal을 문자열로 HTTP JSON 전송.
- [x] desktop ApiClient GET/POST/PATCH 및 엄격한 응답 변환, HTTP mock 테스트.
- [x] TreatmentForm 날짜/금액/입력 규칙과 TreatmentPage 비동기 상태, 사용자 흐름 테스트.
- [x] 메뉴/세션 어댑터/고객 바로가기/이탈 보호 통합 테스트.
- [x] 독립 데모로 큰 창과 최소 창의 레이아웃 확인.
- [x] Ruff/mypy/desktop 및 server/common 테스트, 변경 이력·로드맵·인수 조건 갱신.

## 완료 판정

유효한 기록은 재조회 가능하고 수정은 동일 ID를 유지한다. 빈/유효하지 않은 날짜·음수/범위를 벗어난 금액은 거부한다. 실패하면 입력을 유지하며 다른 고객 응답이 섞이지 않는다. 다른 조직 및 읽기 사용자 쓰기를 서버가 거부한다. 외부 결제·재고·사진·상태 전이는 구현했다고 표시하지 않는다.

검증 완료: desktop 109, server/common 123, Ruff 및 mypy 63개 소스 통과. 실환경 미검증 제한은 제품 문서에 기록.
