# N1030-06 / MED-002 사진 주기 정리·복구 안내

1~5번 완료 뒤 순차 구현한다. 기존 SQL100 pending→ready/failed, 객체 크기·MIME 검증·130분 여유와 기존 정상 사진을 보존한다. SQL 번호/선행 함수는 parent의 최신 ledger를 먼저 확인한다(예상106).

## 해야 할 연결

- 고객 사진 목록 조회가 없어도 내부 스케줄러가 제한된 배치로 pending을 처리한다. Supabase pg_cron 사용 가능 여부/공식 문법을 확인하며 전역 정리 함수는 private에 두고 PUBLIC/anon/authenticated에서 직접 실행하지 못하게 한다. JWT 없는 cron이 공개 사용자 RPC의 auth 검사에 걸리지 않도록 내부 구현과 사용자 진입점 검사를 분리한다.
- 1회 최대250행/실행시간 제한과 SKIP LOCKED 등 동시 작업 보호를 적용한다. 아직 전송 중인 오래되지 않은 행250개 때문에 뒤의 실제 완료/만료 행 처리가 계속 막히지 않도록 대상 선택을 설계한다. 중복 스케줄/수동 조회와 동시에 실행해도 중복/깨진 상태가 없어야 한다.
- 자동 복구는 실제 객체 크기와 MIME가 일치할 때만 ready. 서명 URL 유효2시간+10분 유예 내 객체가 없다고 실패 처리하지 않는다. 만료 뒤 missing/mismatch는 명시적 원인과 failed로 격리한다. 기존 활성 사진을 임의 삭제하지 않는다.
- 물리 Storage 객체 삭제는 이번 범위가 아니다. 고객 활동·시술·거래·보관 정상 사진·법적 보유 자료를 유지한다. 자동 작업은 필요한 메타데이터 상태만 갱신한다.
- 관리자에게 pending/failed 등록의 원인·시각과 '사진 다시 선택' 재등록 동선을 제공한다. 만료/불확실한 옛 서명 URL을 재사용하지 않는다. 파일이 실제 기기에 없는데 자동 재전송되는 것처럼 표시하지 않는다. 등록 실패/저장 중 입력 보호와 조직/권한 검사를 보존한다.
- 기존 공개 reconcile RPC/클라이언트 계약을 깨지 않고 내부 공통 구현을 재사용한다. 서버에서 주기 작업 최근 실행/실패를 조회할 수 있으면 관리자 진단에 최소 결과를 표시하며 고객명/번호/사진 URL을 로그에 넣지 않는다.
- 4/5번의 전화/번호부 변경 로그 만료 정리 인터페이스가 준비돼 있으면 별도 제한된 내부 cron과 연결하되, 원장의 명시적 보유기간을 넘어서 다른 자료를 삭제하지 않는다.

## 집중 검증

격리 PostgreSQL에서 실제 객체/메타데이터 조건, 130분 경계, 반복 실행·상태 경쟁·fresh pending의 뒤 대상 starvation, 다른 조직/anon 권한을 검증한다. pg_cron extension은 로컬 PGlite에서 없을 수 있으므로 scheduler SQL 계약과 실제 원격 cron 등록/함수 권한 확인을 분리한다. React pending/failed·재등록 실패/재시도·기존 갤러리 회귀를 실행한다.

전체 테스트/실제 앱·실사진 업로드·원격 적용·커밋/푸시 금지. parent가 SQL/스케줄을 검토하고 직접 적용한다. broad README/changelog/ledger는 parent 소유. 결과는 `docs/product/audits/2026-11-02-photo-upload-maintenance.md`에 변경 파일·SQL/API·명령/결과·운영 한계를 기록한다.
