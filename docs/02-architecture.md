# 아키텍처

## 문서 상태

### 현재 구현

현재는 공통 타입·환경설정, FastAPI 상태 확인 API, 그리고 PySide6 최소 화면과 메뉴 카탈로그만 구현되어 있습니다. `AuthPort`와 `StoragePort`는 향후 공급자 연결을 위한 인터페이스 정의일 뿐이며, 실제 Auth 연결, 데이터베이스 접근, RLS, 연결 풀링, 구독 권한 강제, 구조화된 운영 오류 응답은 아직 구현되지 않았습니다.

### 목표 설계

아래 내용은 후속 단계에서 구현할 목표 아키텍처입니다. 현재 실행 가능한 기능으로 해석해서는 안 됩니다.

## 신뢰 경계 (목표 설계)

데스크톱 앱은 사용자가 설치하는 프로그램이므로 신뢰할 수 없는 영역으로 봅니다. 앱에는 Supabase 서비스 키나 데이터베이스 비밀번호를 넣지 않으며, 데이터베이스에 직접 연결하지 않습니다. 모든 보호된 요청은 HTTPS로 FastAPI 서버에 보내고, 서버가 토큰·조직·역할·구독 권한을 다시 확인합니다.

```text
PySide6 Desktop → FastAPI Server → Supabase Auth / PostgreSQL / Storage
```

## 구성 요소의 책임 (목표 설계)

- **데스크톱**: 로그인 화면, 메뉴와 업무 화면, 로컬 파일·Excel·PDF 처리, 서버 API 호출을 담당합니다.
- **서버**: 인증 검증, 조직과 역할 확인, 구독·기능 권한 판단, 업무 규칙, 감사 로그를 담당합니다.
- **공통 패키지**: 앱과 서버가 함께 쓰는 순수 타입과 API 계약을 담당합니다.
- **Supabase**: Auth, PostgreSQL, Storage를 제공합니다. 서비스가 바뀌어도 영향이 작도록 서버의 공급자 포트 뒤에 둡니다.

현재 `AuthPort`는 access token 검증을, `StoragePort`는 파일 업로드 URL 발급을 위한 계약만 정의합니다. 목표 구현에서는 실제 Supabase 연결 코드를 이 포트를 구현하는 어댑터에만 둡니다.

## 요청 흐름 (목표 설계)

로그인에서는 데스크톱이 서버에 인증을 요청하고, 서버가 Auth 공급자에 인증을 맡긴 뒤 세션 정보를 돌려줍니다. 이후 요청은 access token을 HTTPS Authorization 헤더에 담습니다.

메뉴를 만들 때는 데스크톱이 권한 목록을 요청합니다. 서버는 조직 멤버십과 활성 구독을 읽어 기능 코드를 계산하고, 데스크톱은 그 결과로 메뉴를 표시합니다. 실제 업무 API도 같은 기능 코드를 다시 검사합니다.

## PostgreSQL 테넌트 격리와 연결 (목표 설계)

모든 업무 데이터에는 `organization_id`를 넣습니다. PostgreSQL Row Level Security(RLS) 정책으로 현재 조직 밖의 행을 읽거나 바꾸지 못하게 하고, 서버의 권한 검사도 함께 적용합니다. RLS는 서버 코드의 실수를 막는 두 번째 안전망입니다.

외래키와 `organization_id` 같은 테넌트 필터 열에는 필요한 인덱스를 둡니다. 서버는 Supabase 트랜잭션 풀러를 사용하고 연결 풀 크기를 제한해 많은 요청이 한꺼번에 와도 연결을 과도하게 만들지 않습니다.

## 오류와 로그 (목표 설계)

API 오류는 안정적인 오류 코드, 사용자가 이해할 메시지, 문제 추적용 ID를 함께 반환합니다. 예: 인증 실패는 `AUTH_INVALID_TOKEN`, 권한 부족은 `AUTHORIZATION_DENIED`, 구독 만료는 `SUBSCRIPTION_EXPIRED`, 입력 오류는 `VALIDATION_ERROR`입니다.

로그에는 추적 ID와 필요한 운영 정보만 구조화해 기록합니다. 비밀번호, access token, 서비스 키, 데이터베이스 URL, 민감한 고객 정보는 절대 로그에 쓰지 않습니다. 네트워크 단절과 인증 만료는 데스크톱에서 서로 다른 안내를 보여 줍니다.
