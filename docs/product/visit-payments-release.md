# 방문 수납·부분 수금 적용 안내

작성일: 2026-10-06 · 기능: SALE-001 / SALE-002 · 담당: Codex  
상태: 로컬 구현·범위별 검증 완료, 실환경 인수 전 `in-progress`

## 사용할 수 있는 흐름

매출·지출 → 결제 장바구니 → 고객과 방문 선택 → 시술 초안 담기 → 금액 검토 → 검토 완료 → **수납 기록 · 내역**.

현금·카드·이체 금액을 나누어 입력하고 카드 승인번호/이체 식별번호를 기록한다. 실제로 받은 사실을 확인한 뒤 저장한다. 10만원을 카드 7만원+현금 3만원으로 기록하거나, 일부만 받은 뒤 남은 미수를 이어서 기록할 수 있다. 완납 방문도 방문 목록에서 다시 열어 수납 내역을 확인한다.

이 화면은 외부에서 받은 금액을 기록한다. 카드 단말기 승인이나 은행 송금을 실행하지 않는다. 첫 수납 뒤 청구 항목은 동결하며, 잘못된 수납을 직접 수정·삭제하는 기능은 없다. 환불/정정은 SALE-003의 별도 원장 작업으로 남아 있다. 원 미만 소수가 있는 청구는 수납 전 장바구니에서 정정한다.

## 이번 구현

- DB의 방문·장바구니·항목 단일 스냅샷 조회. 잘못된 수량/금액/버전/null 입력 거부.
- 사용자까지 일치하는 요청 재시도, 장바구니→방문 잠금 순서, 검토 후 항목 변경 시 재검토 상태로 전환.
- 문서 편집 기능 없이 CRM+finance 권한으로 기존 시술 청구 초안 조회.
- 원 단위 KRW 복합 수납, 부분 수금, 과수금 방지, 카드/이체 확인 번호 중복 방지.
- 첫 수납부터 장바구니 변경 차단, 완납 시 방문 종료.
- 영수 행과 재무 수입행을 같은 DB 트랜잭션에서 생성. 연결된 재무행은 범용 수정·보관·삭제로 변경 불가. 한국시간 기준 거래일.
- 복합 외래 키와 검증 트리거로 다른 조직·방문·금액·작성자의 재무행 연결 거부.
- 저장 전 입력 보호, 처리 중 중복 조작 차단, 화면 재실행 후 동일 요청 재시도. 복구 정보는 서버 주소+사용자+조직+방문별로 분리한다. 통신 결과 불명 후 로그인 만료/권한 오류가 나도 요청 ID를 버리지 않는다.
- 복구 정보 보관 실패 시 수납 요청을 보내지 않는다. 정리 실패 시 새 기록을 막고 기존 요청으로 결과를 재확인한다.

## SQL 적용 순서

실제 Supabase에는 이번 작업에서 아무것도 실행하지 않았다. 새 서버/앱을 사용하기 전에 대상 DB의 적용 기록을 확인한다.

1. 001~023이 적용된 DB: `024_visit_sale_carts.sql` → `025_visit_payments.sql` → `026_sale_cart_hardening_upgrade.sql`.
2. 이전 024가 이미 적용된 DB: 024를 다시 실행하지 않고 **025 → 026**을 실행한다.
3. 025까지 적용한 DB: **026**으로 장바구니 함수 보완을 반영한다. 026은 테이블과 데이터를 다시 만들지 않고 함수만 교체한다.
4. SQL을 모두 적용한 뒤 같은 버전의 서버와 데스크톱을 재시작한다. 이전 서버와 새 수납 앱을 섞어 운영하지 않는다.

026의 반복 실행과 이미 완납한 방문의 영수증·합계 보존을 격리 DB에서 확인했다. 이 기록은 실환경 적용 성공을 의미하지 않는다.

이번 Python 검증은 앱에 포함된 **Python 3.12.14 보조 환경**에서 수행했다. 기본 `.venv`의 Python 3.13은 `uv trampoline ... os error 4551`로 실행되지 않아 지원 대상 환경 검증을 완료하지 못했다. 보조 환경은 자체 pydantic/pydantic_core를 먼저 불러온 뒤 기존 Python 패키지 경로를 추가했다. 이를 Python 3.13 통과로 해석하지 않는다. 회사 PC 보안 설정을 변경하지 않았다.

## 실환경에서 남은 인수

- 지원 대상 Python 3.13 PC에서 서버/앱 실행과 전체 회귀.
- 별도 테스트 조직에서 관리자/멤버와 두 앱 세션으로 동시에 같은 장바구니 수납 시 한 요청만 반영되는지 확인.
- 실제 네트워크 단절·재로그인·앱 재실행 후 복구 및 대시보드 재무 집계 연결 확인.
- 수납 후 당일 거래 내역 조회, 재무 합계, 한국시간 자정 경계 확인.

PGlite는 직렬 실행이므로 실제 PostgreSQL 다중 연결 잠금 경합/교착 검증을 대체하지 않는다. 운영 DB 변경, 외부 결제 승인, 배포, 커밋은 하지 않았다.
