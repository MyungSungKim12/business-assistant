# 사진·자료

갱신일: 2026-09-18 · 상태: planned

## 목적·진입점

고객 사진과 거래 증빙 및 교육 자료를 원천 기록에 안전하게 연결한다. 업무 화면에서 진입하고 관리자용 설정은 공통 설정에 둔다.

## 데이터 계약

media_id, organization_id, customer_id, treatment_id, storage_path, content_type, size, checksum, captured_at, category. 식별자에는 조직 경계를 적용한다. 기존 API에 없는 필드는 구현 전에 계약과 마이그레이션을 검토한다.

## 업무·복구 흐름

파일 선택 → 고객/시술 연결 확인 → 검증 → 업로드 → 서버 등록 → 썸네일 생성. 실패한 파일만 재시도하고 등록만 된 고아 파일은 정리 대상으로 추적한다.

## 인수 조건

- [ ] A고객에 업로드 중 B고객으로 이동해도 A의 사진은 A에만 연결된다. 만료된 다운로드 URL을 갱신하고 접근 불가를 빈 사진으로 숨기지 않는다.
- [ ] 오류·권한 부족·취소 결과를 사용자에게 표시하고 작성 중 입력을 보존한다.
- [ ] 성공 재시도·중복 이벤트·다른 조직 접근 사례를 테스트한다.

## 단계·검증 기록

소비 메뉴의 P0 흐름에 필요한 최소 기능부터 제공하고, 확장 기능은 별도 검증한다. 2026-09-18 문서 작성; 2026-09-29 고객 사진 업로드 API·화면 연결 구현 시작. 2026-10-01 MED-002의 백그라운드 업로드, 고객 ID 고정, 실패 파일 보존·재시도 UI를 구현하고 데스크톱 174개 회귀를 통과했다. 실환경에서는 Supabase에 `022_customer_photos.sql`과 `023_customer_photo_storage_bucket.sql`을 적용해야 하며, 실제 전송 진행률·원본/썸네일 분리·고아 파일 정리는 아직 남아 있다. 상태 변경 시 [변경 이력](../changelog.md)에 증거와 제한을 기록한다.

### MED-002 후속 구현 — 2026-10-01

전송 클라이언트가 64KiB 단위로 데이터를 공급하며 전송량을 Qt 신호로 알린다. 100%는 전송 데이터 공급 완료이며 서버 성공 응답 전에는 확인 중으로 표시한다. 취소는 다음 데이터 청크 전에 적용되며 진행 중인 소켓 통신은 타임아웃/응답까지 기다릴 수 있다. 서버 성공 응답을 받은 경우 늦은 취소 클릭보다 성공 결과가 우선한다.

실패·취소 시 해당 업로드에서 만든 사진 기록만 기존 보관 API로 정리한다. 보관 정리 실패를 별도 메시지로 표시한다. 이는 Storage 객체 영구 삭제나 고아 객체 정리가 아니다. 선택 파일은 재시도용으로 유지하고 다른 고객을 선택한 동안 재시도 버튼은 숨긴다. 사진 다운로드 오류를 빈 목록으로 캐시하지 않으며 조회 실패와 사진 새로고침을 제공한다.

남은 범위: 서버 준비 단계 실패 보상, 요청 응답 유실 복구, 서버 완료 확정/썸네일 파이프라인, 오래된 고아 객체 정리, 실제 Storage 왕복, 앱 종료 후 재시도 복구. 실환경 검증 완료를 주장하지 않는다.
