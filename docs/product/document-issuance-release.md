# 고객·시술 문서 자동 채움과 발행본 적용 안내

2026-09-23 · DOC-002 / DOC-003 · 코드 구현 완료, Python·Qt·실환경 검증 대기.

## 사용 흐름

1. 문서 자동화 → 동의서·서식 관리에서 초안을 작성한다. 본문 위의 **자동 채움 항목 삽입**으로 필요한 고객·시술 항목을 넣고 저장/게시한다.
2. 시술관리에서 고객과 저장된 시술을 선택하고 **문서 발행·이력**을 연다. 시술 수정 중이면 먼저 저장해야 한다.
3. 게시된 서식을 선택하고 **최신 정보로 미리보기**를 누른다. 고객명·연락처·시술명·시술일과 자동으로 채워진 본문을 확인한다.
4. 누락 항목이 없을 때 검토 체크 후 발행한다. 검토 중 원본이 바뀌면 발행하지 않고 다시 검토하도록 안내한다.
5. 발행 이력에서 당시 본문·서식 버전·발행자·발행 시각·고객/시술 정보를 조회한다. 발행본은 수정하거나 지우지 않는다.

발행은 **서명 미확인** 상태다. 실제 고객 서명·교부·철회(DOC-004), PDF 출력/전송, 수납·결제 전달은 포함하지 않는다. 기존 범용 문서의 완료 상태도 서명 완료로 취급하지 않는다.

## 자동 채움 항목

| 항목 | 서식 표시 | 미등록 처리 |
| --- | --- | --- |
| 고객 이름 | `{{customer.name}}` | 해당 표시 사용 시 발행 차단 |
| 고객 연락처 | `{{customer.phone}}` | 해당 표시 사용 시 발행 차단 |
| 고객 생년월일 | `{{customer.birth_date}}` | 해당 표시 사용 시 발행 차단 |
| 시술명 | `{{treatment.name}}` | 해당 표시 사용 시 발행 차단 |
| 시술일 | `{{treatment.date}}` | YYYY-MM-DD |
| 담당자 | `{{treatment.practitioner}}` | 해당 표시 사용 시 발행 차단 |
| 예정 금액 | `{{treatment.amount}}` | 0은 유효, 미입력은 발행 차단. 결제 실적 아님 |
| 상담 목표 | `{{treatment.consultation_goal}}` | 해당 표시 사용 시 발행 차단 |

표시 안에 공백을 넣거나 지원하지 않는 항목·잘못된 중괄호를 쓰면 발행을 차단한다. 고객 데이터 안의 중괄호를 다시 자동 치환하지 않는다. 본문은 일반 텍스트이며 HTML을 실행/렌더링하지 않는다. 서식/최종 본문은 최대 100,000자다. 본문 수정은 서식 새 버전에서 진행한다.

## 무결성·복구

- 시술·고객·서식은 같은 조직으로 제한한다. API는 `crm.basic`과 `document.template` 모두 검사한다. 조직 회원은 조회/미리보기만, owner/admin만 발행한다. DB도 조직과 역할을 검사한다.
- 미리보기에는 원본 고객/시술 정보와 변경 지표를 포함한다. 발행할 때 DB에서 원천 행을 잠그고 다시 계산한 결과가 검토본과 완전히 같은지 비교한다. 사용하지 않은 프로필 필드의 변경도 재검토를 요구할 수 있다.
- 발행본은 별도 `issued_treatment_documents`에 당시 본문·게시 버전·원천 스냅샷을 보존한다. 발행자/시각은 DB에서 결정한다. 고객/시술/서식/발행자 삭제는 관련 이력을 지우지 못하도록 제한한다.
- 통신 실패로 결과가 불명확하면 같은 작업 ID로 재시도한다. 이미 성공한 요청은 원본 변경/서식 폐기 후에도 기존 발행본을 반환한다. 다른 요청에 같은 ID를 재사용하면 충돌한다.
- 미확인 요청이 남으면 서식 전환과 추가 발행을 막는다. 처리 중 닫기를 막고, 검토 중/결과 불명확 상태에서 닫기는 확인을 받는다. 이력 조회 오류를 '이력 없음'으로 표시하지 않는다.
- 발행 이력은 현재 시술관리에서 진입한다. CRM 통합 타임라인과 기존 일반 문서 목록으로의 통합, 대량 이력 페이지네이션은 후속 범위다.

## 적용과 다른 PC 검증

실제 Supabase에는 적용하지 않았다. 대상 DB와 백업 확인 후 기존 앱의 쓰기를 중지하고, 기존 007·014 및 016→017→018까지 적용된 스키마에 **019_treatment_document_issuance.sql**을 적용한다. 서버와 데스크톱을 같은 코드로 재시작한다. 기존 동의 사실이나 서명을 임의 이관하지 않는다.

```powershell
uv run --package business-assistant-server pytest apps/server/tests packages/common/tests -q --tb=short
uv run --package business-assistant-desktop pytest apps/desktop/tests -q --tb=short
uv run --package business-assistant-desktop mypy apps/desktop/src apps/server/src packages/common/src
npm test --prefix scripts/db-tests
uv run ruff check .
uv run ruff format --check .
```

실제 화면에서 위 사용 흐름과 빈 서식/미등록 연락처/금액 0/담당 미등록/서식 폐기/고객 정보 변경/통신 실패 재시도/닫기 취소를 확인한다. 조직 관리자·회원·다른 조직 계정으로 접근 경계를 검증한다. 별도 두 클라이언트에서 원본 변경과 발행의 동시성, 실제 PostgREST JSON 응답을 확인한다. 화면 캡처와 테스트 결과를 기능 문서에 추가한 뒤 verified 여부를 판단한다.

## 이번 검증 증거

- `npm test --prefix scripts/db-tests`: 50개 묶음 통과(시술15 + 상담12 + 서식10 + 발행13). 실제 migration 019를 격리 PostgreSQL/PGlite에서 실행했다. 실제 운영 DB·전체 migration 체인·동시 다중 연결·JWT 검증은 아니다.
- 발행 테스트: 정확한 미리보기, 금액 0/누락 구분, 알 수 없는 치환자/형식/길이 제한, 단일 치환, 원본 변경 거절, 재시도, 역할·조직 경계, 직접 쓰기 금지, 폐기 후 과거 발행본/재시도 보존, 원천 삭제 제한.
- Ruff check 및 format 검사 통과. 별도 읽기 전용 검토에서 중요한 결함 발견 없음. 회사 PC 정책으로 Python pytest/mypy·Qt 육안 확인은 미실행이며 신규 화면 캡처도 없다. 기존 실행 결과를 이번 변경의 검증으로 사용하지 않는다.
- 작성일 9월22일의 [구현 계획](../superpowers/plans/2026-09-22-document-issuance.md)을 9월23일 이어서 마무리했다. 별도 커밋·배포·실데이터 변경 없음.
