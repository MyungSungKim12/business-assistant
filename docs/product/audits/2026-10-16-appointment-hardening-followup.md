## 사용자에게 필요한 SQL

사용자 보고상 059까지 적용했다. 다음은 **`migrations/060_storage_archive_access.sql` 하나**다. 기존 001~059를 다시 실행할 필요가 없다. 데이터·사진을 삭제하는 SQL이 아니며, 060은 반복 적용을 격리 DB에서 확인했다.

적용 후 활성 사진·파일의 일반 조회와 업로드, 보관 후 조회 차단, 관리자 복원 후 조회를 실계정으로 확인해야 한다. 기존에 발급한 서명 URL은 만료 전까지 유효하므로 즉시 회수까지 보장하는 변경은 아니다. 버킷은 기존 `business-files` 기준이다.

## 검증 방식

- 이전 API·UI 진단 스크립트는 결함을 기대하던 검사에서 **수정된 동작을 기대하는 회귀 검사**로 전환했다. 원래 발견 사실은 최초 감사 문서에 남겼다.
- `pnpm --filter @business-assistant/api exec tsx ../../scripts/audits/2026-10-16-api-reproduction.mts`: 실제 예약·조직 게이트웨이에 모의 HTTP를 주입. 정상 응답과 조직/연결 불일치 거절, 구성원 대기 등록, 담당 가능 직원 제한 검사.
- `pnpm --filter @business-assistant/desktop-react exec vitest run --config audit/vitest.config.ts`: 고객 저장 실패 및 입고 응답 유실 후 팝업 재개 회귀 2건.
- 예약·고객·재고·문서·매출·정산·공통 내비게이션의 변경 관련 테스트만 실행한다. 전체 테스트·실제 앱 실행·운영 데이터 접근은 하지 않는다.
- `node scripts/db-tests/storage-060.mjs`: 보관/복원, 구성원/관리자/타 조직/사용자 없음, 미등록 객체, 잘못된 경로·원장 ID, 버킷, 업로더, 실제 INSERT RLS, SQL 반복 적용을 임시 PostgreSQL에서 검사한다. Supabase Storage 서비스 HTTP 자체의 실환경 검증은 아니다.

최종 실행 명령과 결과는 아래 검증 기록 및 [변경 이력](../changelog.md)에 기록한다.
