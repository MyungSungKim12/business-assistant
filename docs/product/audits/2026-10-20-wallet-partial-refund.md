# WAL-11 금액권 부분 환불 기록

## 구현 범위

- 관리자는 고객 회원권 창에서 서버가 계산한 환불 가능 한도와 잔액 버전을 확인하고, 외부 결제 수단으로 이미 환불한 원 금액을 기록한다. 앱은 카드사/현금 결제를 직접 취소하거나 이체하지 않는다.
- 대상은 활성·미만료 금액형 회원권이며 횟수 잔액이 없어야 한다. 할인 후 판매 줄 금액과 발급 금액이 동일해야 환불 캡을 제공한다. 판매 할인·발급액이 다르거나 횟수/복합 혜택인 경우 잔여 가치를 추정하지 않고 막는다.
- 환불 금액은 현재 잔액과 원 판매가에서 이전 환불액을 뺀 값 중 작은 금액을 넘을 수 없다. 환불은 사유·관리자·operation ID와 함께 원자 기록된다. 지갑 잔액, 재무 지출, 불변 환불 이벤트가 함께 바뀌며 0원이 되면 지갑은 `refunded` 종료 상태가 된다.
- 수당 미리보기는 환불 발생일의 음수 금액을 원 판매 항목에 연결한다. 환불일 규칙을 적용하고 지난 확정 기간은 덮어쓰지 않는다. 확정 정산 기간과 겹치는 날짜면 기록을 막는다.
- 환불 이력은 고객 회원권 창과 회원권 원장 이력에 표시된다. 재시도에는 같은 입력과 operation ID를 사용해 중복 차감·지출을 막는다.

## 검증

- `node scripts/db-tests/wallet-usage.mjs --refund`: 13개 그룹 통과. 기존 금액/횟수/복합 회원권 사용 경로에 더해 SQL 087 두 번 적용, 할인 일치 환불 한도, 관리자 전용, 부분/전액 잔액 차감, 초과 환불·잔액 버전 충돌, 멱등 재시도, immutable 이벤트, 재무 지출, 환불일 수당 음수 줄, 환불 완료 지갑의 변경·사용 차단, 확정 기간 충돌을 확인했다.
- `pnpm --filter @business-assistant/api test -- src/modules/catalog/catalog.test.ts`: 53개 통과. `pnpm --filter @business-assistant/api build` 통과.
- `pnpm --filter @business-assistant/desktop-react test -- src/features/catalog/catalog.test.tsx`: 36개 통과. `pnpm --filter @business-assistant/desktop-react build` 통과. 기존 번들 500 kB 초과 경고가 있다.
- 전체 프로젝트 테스트, 실제 Windows 앱 흐름, 실제 Supabase 조직, 카드사/현금 외부 환불은 실행하지 않았다.

## SQL 적용 및 제한

- SQL 087~092는 Supabase 적용 대기다. 사용자는 SQL 065까지 적용했다고 보고했고, 066~092의 원격 적용은 이 기록에서 확인하지 않았다.
- 적용 순서는 **현재 Supabase에 적용한 최신 번호 다음부터 누락 없이 087까지**다. 087은 075 회원권 양도와 079 수당 정산 스키마가 존재하는 상태에서 실행해야 한다. API 재시작과 데스크톱 앱 갱신 뒤 테스트 조직의 금액권에서 환불 기록, 재무 지출, 잔액, 이력, 수당 미리보기를 서로 대조한다.
- 할인된 회원권, 판매가와 발급 혜택이 다른 경우, 횟수권·복합권, 환불 수수료/법정 공제, PG 자동 환불은 지원하지 않는다. 이 산식과 운영 정책은 별도 결정 대상이다.
- 테스트는 격리 PGlite와 mock API를 사용했다. Supabase 다중 연결 경쟁, RLS 운영 설정, 실제 지점의 결제/정산 인수는 아직 검증되지 않았다.


## 2026-10-20 관리 입력형 환불 확장

SQL 092와 관리자 API/화면에서 실제 외부 환불액, 금액 혜택 제거, 횟수 회수를 각각 받도록 확장했다. 할인·횟수·복합권도 관리자가 매장 정책에 따라 별도 확정해 기록할 수 있으며, 시스템은 잔여 혜택을 현금 가치로 환산하지 않는다. 환불액은 원 결제 금액에서 기존 환불을 뺀 한도 이내이고, 제거 혜택은 현재 잔액 이내여야 한다. 재무 지출은 실제 외부 환불액을 기록하며 불변 이벤트에는 네 변동값을 함께 보관한다.

격리 PostgreSQL 테스트에서 실제 환불액 25원, 금액 혜택 10원, 횟수 1회를 서로 다른 값으로 기록하고 재시도 중복 방지, 한도 초과, 불변 이력, 재무 원장을 확인했다. API 카탈로그 54건과 React 카탈로그 42건 통과. SQL 092는 Supabase 적용 대기이며 실제 정책상 환불액·회수량 적정성은 점주가 확정해야 한다.
