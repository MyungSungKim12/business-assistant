# 2026-10-16 최초 인수 관점 소스 점검

> 후속: 이 문서는 최초 발견 당시의 기록이다. 이후 수정·회귀 검증과 미완료 범위는 [예약 상세·운영 안전성 보완 결과](2026-10-16-appointment-hardening-followup.md)를 확인한다. 진단 스크립트 일부는 수정된 동작을 기대하는 회귀 검사로 전환했다.

## 기준과 범위

- 대상: `D:\ms\business-assistant`의 현재 작업 트리. HEAD `2947fc8`, 브랜치 `main`. 커밋되지 않은 현재 변경도 포함했다.
- 사용자는 SQL 059까지 적용했다고 보고했다. 원격 Supabase 접속·실데이터 변경·설치 앱 기동은 하지 않았다.
- 이전 계획·완료율·테스트 통과 기록을 구현 완료의 근거로 사용하지 않았다. 현재 화면 코드 → API → 게이트웨이 → SQL/RLS를 연결해 읽었다.
- 예약, 고객, 시술, 매출·수납, 회원권, 재고·발주, 직원·서비스, 정산·경영, 문서·사진·파일, 할 일·검색·알림·권한의 대표 업무 경로를 점검했다. 모든 함수와 모든 입력 조합을 검증한 전수 보증은 아니다.
- 소스에서 의심한 항목 중 일부를 모의 HTTP, JSDOM, 격리 PostgreSQL(PGlite)로 재현했다. 전체 테스트와 실사용 흐름 인수는 실행하지 않았다.
- 화면의 실제 글꼴 선명도·배율·잘림·스크롤·터치 조작·Windows 설치 품질은 이번 점검으로 판단할 수 없다.

## 판단

여러 메뉴의 화면과 저장 API가 존재하고, 예약 충돌·수납 복구·원장 변경에 필요한 기반도 있다. 다만 **직원이 예약을 접수하고, 여러 PC에서 일정을 확인하고, 시술과 수납까지 이어서 처리하는 업무**에는 연결 오류와 재시도·갱신·입력 보호 문제가 남아 있다. 메뉴 수를 기준으로 완료율을 표시하기보다 아래 결함과 업무 인수 조건을 기준으로 판단해야 한다.

유지할 기반도 확인했다. 일/주/목록 달력, 직원별 열, 예약 수정·드래그 이동, 소요·버퍼 표시, 필수 공간·장비, 근무시간·휴무, 예약 버전 검사와 SQL의 잠금, 수납·환불의 사용자별 복구 요청 보관, 문서 버전·발행본·서명 증빙 구조, 일반 API의 서비스 키 분리와 Tauri 자격 증명 저장소 사용은 현재 소스에 존재한다. 이는 전체 실운영 통과를 의미하지 않는다.

## 우선 보완할 결함

P1은 실사용 인수 전에 먼저 보완할 항목, P2는 일상 업무의 효율·정확도를 높일 항목이다. `재현`은 이번 점검에서 실행한 증거가 있고, `소스 확인`은 코드 연결로 확인했으나 실제 앱/원격 환경에서 실행하지 않은 항목이다.

### F01 · P1 · 대기 고객 예약 전환이 성공 응답을 503으로 바꾼다 — 재현

- 상황: SQL은 `{appointment, waitlist, replayed}`를 정상 반환한다. 게이트웨이는 이 묶음 자체에 `organization_id`가 있을 것으로 검사한다.
- 원인: `parse()`는 최상위 행의 `organization_id`를 검사하지만 예약 전환 결과에는 해당 필드가 없고 두 하위 객체에 있다.
- 영향: DB에서는 예약과 대기 상태가 저장됐어도 앱은 실패로 표시한다. 동일 요청을 재시도해도 같은 검증에 다시 걸린다. SQL 059를 적용하는 것만으로 이 API 오류가 해결되지는 않는다.
- 근거: `apps/api/src/supabase/appointments.ts:43`, `:78`; `migrations/059_waitlist_idempotent_booking.sql:95`.
- 재현: 정상 HTTP 200·동일 조직의 유효한 묶음을 실제 게이트웨이에 주입했을 때 API 오류 503이 발생했다.
- 보완: 두 하위 객체의 조직·ID·고객·서비스 연결을 각각 검사하고, 정상 묶음은 성공으로 반환한다. 실제 게이트웨이를 통과하는 경계 테스트가 필요하다.

### F02 · P1 · 직원은 일반 예약을 만들 수 있지만 대기 목록은 403 — 재현

- 화면은 직원에게도 대기 등록·상태 변경·예약 전환을 노출한다. SQL 059도 구성원 역할을 허용한다.
- 대기 변경 라우트는 `requireAccess(..., true)`를 사용한다. 공통 권한 함수에서 `true`는 일반적인 쓰기 여부가 아니라 owner/admin 전용 관리 권한을 뜻한다.
- 영향: 같은 직원이 일반 예약은 등록하지만 대기 접수는 처리하지 못한다.
- 근거: `apps/api/src/routes/appointments.ts:6`, `apps/api/src/supabase/organizations.ts:136`, `apps/desktop-react/src/app/Workspace.tsx:59`.
- 재현: 실제 조직 게이트웨이에 member 응답을 주입한 동일 계정에서 일반 예약 201, 대기 등록 403을 관측했다.
- 보완: 예약 업무 권한과 관리자 설정 권한을 구분하고 화면/API/DB의 역할표를 일치시킨다.

### F04 · P1 · 메뉴 이동·종료의 입력 보호가 화면마다 연결되지 않았다 — 소스 확인

### F05 · P1 · 고객 저장 실패 후 고객을 바꾸면 확인 없이 입력을 잃는다 — 재현

### F06 · P1 · 발주/입고의 화면 재시도가 새 요청으로 전송된다 — 재현

- 발주 생성과 입고 버튼은 호출할 때마다 `crypto.randomUUID()`를 만든다. DB의 멱등 처리는 동일 operation ID에만 적용된다.
- 영향: 2개 입고가 저장된 뒤 응답만 유실되고 사용자가 다시 2개를 입력하면, 잔량이 허용하는 한 별도 입고로 기록될 수 있다. 발주 초안도 같은 이유로 중복 생성될 수 있다.
- 근거: `apps/desktop-react/src/features/catalog/PurchaseOrdersDialog.tsx:46`, `:66`; `migrations/058_purchase_orders.sql`.
- 재현: 입고 첫 응답 유실을 모의한 뒤 동일 수량 재입력 시 서로 다른 operation ID 두 개가 발급됐다. 실제 재고 중복 증가는 원격 DB에서 실행하지 않았다.
- 보완: 전송 전 요청 본문과 ID를 보관하고, 결과 미확인 상태에서는 같은 요청을 재확인한다. 기존 수납 복구 방식과 같은 원칙을 적용한다.

### F07 · P1 · 보관 사진 접근 제한이 Storage 정책까지 이어지지 않는다 — 격리 DB 재현

- 앱 API는 보관 사진의 다운로드를 거절하고 휴지통 조회를 관리자에게 제한한다.
- 반면 사진 메타데이터 SELECT와 Storage 객체 SELECT 정책은 조직 구성원 여부만 확인하고 `is_archived`나 실제 메타데이터의 존재를 검사하지 않는다. 일반 파일도 같은 보관 의미를 검토해야 한다.
- 영향: 조직 구성원이 앱 API를 거치지 않고 Supabase Data/Storage API를 사용하면 앱의 보관 접근 제한을 우회할 여지가 있다. 다른 조직 접근이 허용된다는 뜻은 아니다.
- 근거: `migrations/022_customer_photos.sql:23`, `:59`; `apps/api/src/supabase/customer-photos.ts:8`; `apps/api/src/modules/documents/gateway.ts:306`.
- 재현: 저장소의 SQL 022 정책으로 격리 DB를 구성했을 때 member가 보관 사진의 메타데이터와 Storage 객체를 SELECT했다. 실제 서명 URL 발급/다운로드, 원격 정책 상태는 별도 확인 대상이다.
- 보완: 보관·휴지통·복원·영구 삭제의 접근 정책을 정하고 Storage RLS에도 강제한다. 행의 조직 ID와 객체 경로·메타데이터 연결도 검사한다. 구독 만료 후 직접 Data API 접근 정책도 함께 점검한다.

### F09 · P1 · 예약→시술→수납의 공통 업무 문맥이 화면에서 끊긴다 — 소스 확인

- 영향: 고객·예약 서비스·담당자·방문을 메뉴마다 다시 찾고 연결해야 한다. 예약 완료와 시술 완료·수납 상태도 별개라 업무 완료를 오해할 수 있다.

### F11 · P2 · 예약 접수에 고객 검색·즉시 신규 등록이 없다 — 소스 확인

- 예약 폼은 고객 이름만 나열한 select를 사용한다. 동명이인 구분용 연락처, 전화번호 검색, 최근 고객, 예약 중 빠른 신규 등록이 없다.
- 고객은 기존 전체 목록 API로 읽는다. 그 목록에는 5,000건 상한이 있고 Data API의 실제 max_rows 설정에 따라 더 적게 반환될 수 있다. 예약·시술·매출 등의 선택기는 고객관리 화면의 서버 검색을 재사용하지 않는다.
- 영향: 고객 수가 늘거나 신규 고객의 전화 접수가 많을수록 접수 동선이 길어지고 누락·동명이인 선택 위험이 커진다.
- 근거: `apps/desktop-react/src/features/appointments/AppointmentForm.tsx:155`; `apps/api/src/supabase/customers.ts:109`; `apps/desktop-react/src/api/client.ts:92`.
- 보완: 이름/전화번호 검색형 고객 선택기, 연락처 뒷자리, 간편 신규 등록·중복 후보 확인을 예약 폼 안에서 제공한다. 기존 `vip` status와 VIP 태그의 호환·필터 정책도 통일한다.

### F12 · P2 · 발주 품목·파일 등 목록이 Data API 한 페이지로 끝난다 — 소스 확인

- 발주서와 발주 품목을 각각 한 번 SELECT한 뒤 클라이언트에서 결합한다. 파일·폴더도 한 번의 SELECT로 끝난다.
- 영향: 실제 max_rows 한도를 넘으면 일부 발주 품목·파일이 빠져도 ‘전체 목록’처럼 보일 수 있다. 발주서 페이지와 품목 페이지가 다르게 잘리면 특정 발주서가 품목 없는 것으로 보일 수 있다.
- 근거: `apps/api/src/modules/catalog/gateway.ts:107`; `apps/api/src/modules/documents/gateway.ts:265`; `apps/api/src/supabase/rest.ts:56`.
- 보완: 발주서는 페이지별 조회+해당 발주서 품목 조회 또는 DB 묶음 RPC를 사용한다. 목록에는 total/has_more를 반환하고 검색·내보내기 범위를 분명히 표시한다.

### F13 · P2 · 노쇼 사유 입력이 저장된 예약에 남지 않는다 — 소스 확인

- 화면은 노쇼에도 사유를 요구한다. SQL은 사유를 fingerprint에는 넣지만 예약 행의 `cancellation_reason`은 canceled일 때만 저장한다.
- 영향: 운영자가 입력한 노쇼 사유를 예약 상세에서 다시 읽을 수 없다. operation 원장은 존재하지만 사용자용 예약 변경 이력 조회와는 다르다.
- 근거: `apps/desktop-react/src/features/appointments/appointmentRules.ts:32`; `migrations/034_appointments.sql:189`, `:210`; `apps/desktop-react/src/features/appointments/AppointmentDetail.tsx`.
- 보완: 상태 변경 사유를 별도 이벤트로 보존하고 예약 상세에 변경자·시간·이전/이후 상태·사유를 표시한다. 실수로 처리한 노쇼/방문 상태의 관리자 정정도 설계한다.

### F14 · P2 · 직원 퇴사/중지와 고객 주요 정보 입력 동선이 부족하다 — 소스 확인

- 직원 화면은 추가·근무시간·휴무 중심이며 이름 변경·예약 담당 중지 동선이 없다. 로그인 구성원과 예약 담당자의 직접 연결도 없다.
- 고객 스키마에는 생년월일·알레르기·피부 타입이 있지만 현재 고객 폼에는 이름·연락처·이메일·태그·동의·메모만 있다.
- 영향: 퇴사 담당자 관리, 생일 안내, 시술 주의사항을 일반 화면만으로 정비하기 어렵다.
- 근거: `apps/desktop-react/src/features/catalog/StaffPage.tsx`; `apps/desktop-react/src/features/customers/CustomerForm.tsx:6`; `apps/api/src/modules/treatments/schemas.ts`.
- 보완: 과거 이력을 보존하는 담당자 중지·향후 예약 재배정, 구성원과 직원 매핑, 고객 필수 프로필과 시술 전 주의사항 표시를 제공한다.

### F15 · P2 · Native HTTP에 전체 요청 시간 제한이 없다 — 소스 확인

- Rust API 요청은 reqwest Client를 기본 설정으로 만들고, 요청/응답 읽기에 전체 timeout을 지정하지 않는다. 일반 API의 Supabase 호출 10초 제한과는 다른 구간이다.
- 영향: API 연결이 응답하지 않으면 앱의 ‘저장 중’이 오래 지속될 수 있다. 실제 네트워크 장애 시간은 이번에 측정하지 않았다.
- 근거: `apps/desktop-react/src-tauri/src/http.rs:44`.
- 보완: 연결·전체 응답 시간 제한과 취소 신호를 제공한다. 쓰기 요청 timeout은 실패 확정으로 간주하지 말고 같은 ID로 결과를 확인한다.

### F16 · P2 · 가능 시간 조회가 직원 수에 따라 많은 DB HTTP 호출을 만든다 — 소스 확인

- 초기 서비스·직원·자원·필수 조건 4회, 예약 조회 최소 1회, 직원별 가용 정보 조회가 직원 행→근무시간→휴무의 최소 3회다. 페이지가 추가되지 않는 경우에도 데이터 조회만 대략 `5 + 3×직원 수`회다. 인증·권한 조회는 별도다.
- 영향: 담당자 미선택 상태에서 직원 10명이면 최소 약 35개의 데이터 요청이 만들어진다. 병렬화돼 있어도 네트워크 지연·동시 요청·입력 변경이 겹치면 느려질 구조다. 실제 응답 초 단위 수치는 측정하지 않았다.
- 근거: `apps/api/src/modules/appointment-resources/availabilityRoutes.ts:43`, `:56`; `apps/api/src/modules/appointment-resources/gateway.ts:173`.
- 보완: 지정일·직원 범위의 근무·휴무·서비스 배정·예약·자원을 묶어서 읽고, 입력 debounce·요청 취소·짧은 캐시·저장 후 무효화를 적용한다.

## 예약 화면을 업주 중심으로 개선할 항목

아래는 결함 수정과 별도의 제품 보완 제안이다. 존재하는 가용 시간 계산 API와 일/주 달력을 다시 만드는 작업이 아니다.

| 순서 | 개선 | 업주가 얻는 변화 | 인수 조건 |
| --- | --- | --- | --- |
| 1 | 빠른 고객 접수 | 전화번호 검색 → 동명이인 확인 → 없으면 간편 신규 등록 → 예약 폼으로 복귀 | 다른 메뉴 이동 없이 입력·선택 고객을 보존 |
| 2 | 시간/담당/자원 조건 일치 | 선택한 서비스에 실제로 가능한 직원과 시간만 안내 | 안내 가능 슬롯과 SQL 저장 조건이 일치 |
| 3 | 운영 상태가 보이는 달력 | 근무 외·휴무·휴게·자원 사용을 배경으로 구별하고 상태별 표시/숨김 제공 | 빈 시간과 실제 예약 가능한 시간을 구별 |
| 4 | 다인 근무와 주 보기 밀도 | 직원 필터 유지, 겹친 예약 요약/펼침, 취소 건 숨기기, 마지막 동기화 시각 | 동시간대 예약이 많아도 이름/시간을 찾아 열 수 있음 |
| 5 | 예약 상세 업무 버튼 | 고객 프로필·시술·해당 방문 수납으로 바로 이동 | 같은 고객/예약/방문 ID가 유지되며 중복 방문 생성 없음 |
| 6 | 예약 변경 이력·정정 | 취소/노쇼 사유와 변경자 조회, 권한 있는 정정 | 사유가 사라지지 않고 시간 충돌/원장 일관성을 유지 |
| 7 | 여러 서비스 한 번에 예약 | 컷+염색 등 순차 서비스와 담당자별 시간을 구성 | 일부 서비스 충돌 시 전체 저장/부분 저장 규칙이 명확 |
| 8 | 반복·대기 추천·확인 알림 | 반복 회차 예외, 취소 슬롯에 대기 고객 제안, 안내 발송 이력 | 중복 생성/중복 발송 방지, 수신 정책·업무 안내 구분 |

소스상 일/주 달력은 자정 밖 예약에 맞춰 범위를 넓히고 겹침도 계산한다. 다만 주 보기에서는 직원 전체가 한 날짜 열에 모이고 동시간대 n건이 `100/n%` 너비를 나눈다. 실제 화면에서 5·15·30분 예약, 직원 1·5·10명, 긴 고객/서비스 이름, 취소 후 같은 슬롯 재예약, 100/125/150% Windows 배율을 확인해야 ‘잘 보인다’를 판정할 수 있다. 날짜 밖 조회가 start_at 기준인 점 때문에 전날부터 이어지는 예약도 별도 경계 사례로 확인해야 한다.
