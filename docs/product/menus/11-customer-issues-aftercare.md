# 11 고객 이슈·사후관리

갱신일: 2026-09-18 · 담당: 제품/구현 담당자 · 현재 판정: 목표 설계, 실운영 검증 전

## 목적과 사용자

불편 사항과 고객에게 한 약속을 담당자·기한·처리 결과가 있는 업무로 관리한다.

## 화면 구성

접수/처리 중/고객 확인 대기/완료 보드와 기한 초과 필터. 상세에는 원시술·결제·사진·고객 연락 및 내부 기록을 분리한다.

## 기능 추적

| ID | 우선 | 상태 | 구현 범위 |
| --- | --- | --- | --- |
| CARE-001 | P0 | planned | 문의·불편·재시술 요청과 원거래 연결 |
| CARE-002 | P0 | planned | 담당자·처리 기한·진행 상태·처리 결과 |

| CARE-005 | P1 | planned | 처리 후 고객 확인과 재개 |
| CARE-006 | P2 | planned | 제품·시술 과정별 반복 문제 분석 |

## 필드와 업무 규칙

- case_id, customer_id, source_visit_id, source_sale_id, category, severity: 확인한 사실과 추정 원인을 분리한다.
- owner_id, due_at, status, resolution, verified_at: 완료와 고객 확인 완료를 구분한다.
- promise_id, promised_action, promised_at, due_at, completion_reference: 완료 근거가 없는 약속은 자동 완료하지 않는다.
- internal_notes, customer_visible_summary: 공유 범위를 구분한다.

## 정상·취소·실패 흐름

1. 접수 → 담당 배정 → 고객과 처리 방안 합의 → 환불/재시술 실행 → 고객 확인 → 완료.
2. 담당자 부재·퇴사 시 인수인계 대상에 포함하고 재배정한다.
3. 같은 문제가 재발하면 이전 사례를 연결하여 재개한다. 과거 처리 기록을 지우지 않는다.

## 연동과 단계

CRM 고객/약속, TRT 시술·사진, SALE 환불, TEAM 인수인계, MKT 답변.

1차는 P0의 실제 업무 흐름과 복구 경로를 검증한다. P1은 기본 데이터와 정정 흐름이 안정된 뒤 구현한다. P2는 외부 연동 계약 또는 충분한 데이터가 확보된 뒤 진행한다. 기존 범용 메뉴/API가 일부 있어도 이 문서의 기능 완료로 간주하지 않는다.

## 인수 조건

- [ ] 담당자가 바뀌어도 약속과 기한이 사라지지 않는다.
- [ ] 환불 제안을 입력하는 것만으로 실제 환불이 실행되지 않는다.
- [ ] 기한 알림 재실행이 동일 담당자에게 중복 업무를 생성하지 않는다.
- [ ] 다른 조직 데이터 접근과 권한 없는 변경이 서버에서 거부된다.
- [ ] 빈 상태·로딩·실패·재시도·동시 변경 시 사용자가 현재 상태를 알 수 있다.
