갱신일: 2026-09-18 · 담당: 제품/구현 담당자 · 현재 판정: 목표 설계, 실운영 검증 전

## 목적과 사용자

직원이 판매·사용·환불을 처리하고 고객에게 잔여 혜택의 근거를 설명한다.

## 필드와 업무 규칙

- wallet_id, customer_id, product_version, purchase_sale_id: 판매 당시 상품 조건을 스냅샷으로 저장한다.
- ledger_id, operation, money_delta, count_delta, original_ledger_id: 잔액은 원장으로 재계산 가능해야 한다.
- valid_from, expires_at, paused_periods, allowed_services: 유효기간 경계는 매장 시간대로 계산한다.
- 할인 판매 금액과 제공 혜택을 분리한다. 회차별 가치·환불 계산 방식은 운영 정책으로 명시하고 저장한다.

## 정상·취소·실패 흐름

1. 상품 선택 → 판매 조건 안내 → 결제 확정 → 지갑 개설 → 고객 잔액 표시.
2. 시술 완료/결제 시 적용할 지갑 선택 → 사용 가능·유효기간 검증 → 차감 원장 기록.
3. 시술 취소 → 해당 차감 원장의 반대 거래 생성. 이미 취소한 차감은 다시 복원하지 않는다.
4. 연장·정지·환불은 권한과 사유를 요구하고 기존 기록을 덮어쓰지 않는다.

## 연동과 단계

SALE 결제 확정 및 환불, CRM 고객, TRT 차감 대상 시술, APT 수용량.

1차는 P0의 실제 업무 흐름과 복구 경로를 검증한다. P1은 기본 데이터와 정정 흐름이 안정된 뒤 구현한다. P2는 외부 연동 계약 또는 충분한 데이터가 확보된 뒤 진행한다. 기존 범용 메뉴/API가 일부 있어도 이 문서의 기능 완료로 간주하지 않는다.

## 인수 조건

- [ ] 잔여 1회에 두 직원이 동시에 차감하면 하나만 성공하고 음수 잔액이 생기지 않는다.
- [ ] 차감 취소 재전송에도 1회만 복원된다.
- [ ] 같은 상품의 가격이 바뀌어도 기존 고객의 구매 조건과 원장은 유지된다.
- [ ] 다른 조직 데이터 접근과 권한 없는 변경이 서버에서 거부된다.
- [ ] 빈 상태·로딩·실패·재시도·동시 변경 시 사용자가 현재 상태를 알 수 있다.
