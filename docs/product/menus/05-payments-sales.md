# 05 결제·매출

갱신일: 2026-09-18 · 담당: 제품/구현 담당자 · 현재 판정: 목표 설계, 실운영 검증 전

## 목적과 사용자

접수 직원이 방문 건을 빠르게 결제하고 관리자가 취소·환불·마감을 추적한다.

## 화면 구성

왼쪽 방문/고객 선택, 중앙 시술·제품 장바구니, 오른쪽 결제수단과 할인 내역. 하단에는 총액·미수·확정 버튼. 거래 상세는 원거래와 취소 거래를 함께 표시한다.

## 필드와 업무 규칙

- sale_id, customer_id, visit_id, organization_id: 원천 연결; 고객 미지정 판매 허용 여부는 매장 설정으로 고정한다.
- line_id, item_type, item_id, quantity, unit_price, discount, staff_allocation: 금액은 Decimal/최소 화폐 단위로 처리한다.
- payment_id, method, amount, provider_reference, status: 요청/성공/실패/결과불명 상태를 구분한다.
- refund_id, original_payment_id, amount, reason, approved_by: 누적 환불액은 실제 수금액을 초과할 수 없다.
- 사업장별 반올림·세금 표시 정책을 고정하고 거래 확정 시 규칙 버전을 보존한다.

## 정상·취소·실패 흐름

1. 고객/방문 선택 → 항목·할인 검토 → 결제 요청 → 결과 확인 → 영수증·각 원장 반영.
2. 외부 결제가 타임아웃이면 결과불명으로 남기고 동일 키 상태 조회 후 재시도한다. 성공 여부를 모른 채 새 결제를 보내지 않는다.
3. 부분 환불 → 원거래 잔여 환불 가능액 확인 → 승인 → 결제 취소 → 회원권·재고·수당의 해당 부분만 되돌린다.
4. 마감 이후 수정은 원거래를 덮어쓰지 않고 정정 거래로 표시한다.

## 연동과 단계

CRM 고객, APT 방문, TRT 시술 내역, WAL 지갑, INV 재고, TEAM 실적, FIN 정산.

1차는 P0의 실제 업무 흐름과 복구 경로를 검증한다. P1은 기본 데이터와 정정 흐름이 안정된 뒤 구현한다. P2는 외부 연동 계약 또는 충분한 데이터가 확보된 뒤 진행한다. 기존 범용 메뉴/API가 일부 있어도 이 문서의 기능 완료로 간주하지 않는다.

## 인수 조건

- [ ] 10만원을 카드 7만원+현금 3만원으로 수금했을 때 미수는 0원이며 수단별 합계가 일치한다.
- [ ] 동일 결제 요청 재전송은 한 거래만 생성한다. 결과불명 상태에서 확정 매출이 중복 반영되지 않는다.
- [ ] 부분 환불 후 원거래+환불 합계, 지갑 잔액, 재고 및 수당의 조정액이 일치한다.
- [ ] 다른 조직 데이터 접근과 권한 없는 변경이 서버에서 거부된다.
- [ ] 빈 상태·로딩·실패·재시도·동시 변경 시 사용자가 현재 상태를 알 수 있다.
