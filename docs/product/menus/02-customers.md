# 02 고객관리

목적: 접수·상담·시술에 필요한 고객 정보를 한 번 정확히 저장하고, 고객별 기록을 이어서 확인한다. 접수 담당자는 검색·등록, 관리자는 정정·보관·복원, 읽기 역할은 허용된 범위의 조회를 수행한다. 목표 역할 세분화와 현재 owner/admin 변경 권한은 구분한다.

## 화면 구조

왼쪽 네이비 내비게이션 옆 중앙 상단은 이름/전화/태그 검색·상태 필터·건수·3열 고객 카드, 중앙 하단은 프로필 편집이다. 우측은 고객 헤더, 상담 이력/사진/메모 탭과 사진 미리보기다. 고객 미선택과 검색 결과 없음은 별도 상태다. 저장/취소는 편집 영역에 있고 보관/복원은 현재 상태에 맞게 노출한다. 읽기 역할에서는 입력과 변경 행동을 잠그되 이유를 표시한다.

## 업무 흐름

1. 신규: 검색으로 기존 고객 확인 → 등록 폼 → 필수·선택 필드 입력 → 단일 POST로 프로필 전체 저장 → 생성 응답 ID로 상세/목록 동기화. 저장 실패 시 입력 유지, 부분 고객 생성 없이 재시도한다. 결과 불명확한 타임아웃은 목록 확인 후 재시도하도록 안내하고, 서버 멱등 키 도입은 후속 계약으로 둔다.
2. 편집: 고객 선택 → 필드 변경 → 저장/취소. 다른 고객 선택·탭/메뉴 이동·창 종료 시 미저장 변경이 있으면 저장/버리기/계속 편집 선택을 제공한다. 저장 실패하면 이동하지 않는다. 구현에서 보호 가능한 이동 경로는 검증 기록에 명시한다.
3. 보관: 고객 확인 → 보관 안내 → `status` PATCH → 보관 필터에서 확인. 복원은 active PATCH로 동일 ID를 되살린다. 취소하면 상태를 유지한다. 보관은 개인정보 영구 삭제가 아니며 이력 연결을 끊지 않는다.
4. 기록: 고객별 활동 조회 → 메모 제목/내용 입력 → 생성 → 서버 반환 기록을 같은 고객 타임라인에 반영. 고객 전환 중 늦게 도착한 이전 응답이 현재 고객 화면에 섞이지 않아야 한다.

## 필드 계약과 규칙

현재 API 소스에서 아래 프로필 필드와 활동 필드를 확인했다. 길이는 현재 명시적 검사와 목표 검사를 구분한다. 공백·날짜·배열 검증의 실제 적용 범위는 CRM-001 검증 시 확정한다.

| 필드 | 입력·표시 규칙 |
| --- | --- |
| id, organization_id | 서버 식별자; 조직 간 고객 접근 불가 |
| name | 필수, 앞뒤 공백 제거 후 1~200자; 동명이인 허용 |
| phone | 선택, 빈 값은 null, 현재 최대 50자; 표시값과 숫자 중심 검색키 구분; 전화 공유만으로 중복 단정 금지 |
| email | 선택, 빈 값은 null; 현재 @ 포함·최대 320자 검사; 배송 가능 검증과 구분 |
| birth_date | 선택, 날짜 형식·유효 날짜 확인 목표; 나이는 생일 기준으로 표시하고 저장하지 않음 |
| skin_type | 선택 분류; 미입력을 특정 타입으로 자동 변환하지 않음 |
| concerns | 다중 관심사 문자열 배열; 빈 항목·중복·공백 정리 목표 |
| allergies | 자유 텍스트; 미입력을 '알레르기 없음'으로 해석하지 않음 |
| notes | 기본 빈 문자열, 현재 최대 5,000자; 프로필 메모와 개별 활동 기록 구분 |
| last_visit_date, next_visit_date | 선택 날짜; 1단계 수기 정보임을 표시, 예약/시술 연동 전 자동 확정 정보로 취급하지 않음 |
| tags | 문자열 배열; 공백 제거·중복 정리 목표; 이름/전화와 함께 검색 |
| status | active/archived 목표 계약; 기존 데이터 상태값과 호환 검사 필요 |
| activity_type, title | 현재 각각 1~100자, 메모 기본 유형 note |
| description, occurred_at | 현재 설명 최대 10,000자, 발생 시각 선택; 표시 정렬과 시간대 일관성 검증 |

수정 요청의 '필드 미전송'은 유지, 명시적 null/빈 문자열은 해당 필드 계약에 따라 지우기다. 이름 null은 거부한다. 고객 수는 조회 가능한 전체/현재 필터 결과를 구분하고 페이지 건수를 전체 건수처럼 표시하지 않는다.

## 의존성과 인수 조건

기초 단계는 고객 API, 활동 API, 조직 역할, `crm.basic`에 의존한다. 예약·지갑·사진 연결은 APT/WAL/MED가 검증되기 전까지 계획 상태로 둔다.

- CRM-001: 모든 지원 필드를 채워 한 번 등록 후 재조회해 값이 보존된다. 잘못된 필드 한 개로 요청이 실패하면 고객의 일부 정보만 생성되지 않는다.
- CRM-002: 보관 후 기본 active 목록에서 빠지고 archived 필터에서 조회된다. 복원 후 ID와 활동이 유지된다. API 삭제를 호출하지 않는다.
- CRM-003: `010-1234-5678`로 저장한 고객을 `01012345678`로 찾는다. 이름 앞뒤 공백·영문 대소문자·태그 검색 사례와 필터 건수가 일치한다.
- CRM-004: A고객의 활동이 B고객에 섞이지 않는다. 생성 실패 시 내용이 보존되고 성공 후 해당 고객 기록에만 나타난다.
- CRM-005: 고객 변경·메뉴 이탈·창 종료 각 경로에서 버리기 전 입력 유실이 없다. 저장 실패 후에는 현재 편집 화면을 유지한다.
- CRM-006: 읽기 역할은 수정/보관/활동 생성 불가이며 직접 API 요청도 거부된다. 목록과 상세 조회 권한은 유지된다.
- CRM-007: 실제 사진이 없는 신규 고객에게 다른 사람의 사진이나 데모 시술을 보여주지 않는다. 데모를 선택한 경우 데모 표시가 식별된다.
- CRM-008 이후: 병합 참조 재연결, 감사 무결성, 약속 알림의 중복 방지, 외부 원천 장애 처리는 각 기능 구현 전에 별도 사례를 확정한다.

## 단계와 검증 기록

1단계 CRM-001~007, 2단계 감사·약속, 3단계 병합·원천 통합. 2026-09-17: 고객·활동 API 소스와 필드 존재를 읽기 확인. 당시에는 in-progress였으며, 최신 구현·검증 상태는 아래 2026-09-18 기록을 따른다. 단일 CRUD나 디자인만으로 상용 CRM 완료를 주장하지 않는다.

현재 제한/다음 작업:

- 실제 배포 서버의 등록·수정·보관·활동 영속성 왕복 검증은 하지 않았다. 테스트는 fake client/HTTP mock 및 기존 서버 테스트다.
- 고객 프로필 조회/저장은 기존 동기 HTTP 방식이다. 대량 고객 페이지네이션·검색 서버화·프로필 요청 비동기화·성능 측정은 별도 개선 대상이다. 활동 조회/저장은 이미 비동기화했다.
- 프로필 생성은 단일 요청이지만 서버 멱등 키는 없다. 응답을 잃은 타임아웃의 중복 생성 방지까지 보장하지 않는다.
- 변경 감사/약속/병합 및 예약·회원권·정식 시술/사진 원천 통합은 CRM-008~011의 계획 상태를 유지한다.
- 활동의 `treatment`는 시술 메모이며 정식 시술 완료나 재고/매출을 확정하지 않는다. 프로필의 방문일은 수기 정보다.
