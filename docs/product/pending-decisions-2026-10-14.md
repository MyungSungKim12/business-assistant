## 2. 외부 서비스가 필요한 것 (모아서 진행)

### D-01 문자·알림톡 발송
- **하고 싶은 일**: 재방문 안내, 예약 전날 안내, 생일, 장기 미방문 고객 연락(CRM-13), 예약 알림 문자(APT-13), 문서 전송(DOC-11).
- **지금 상태**: 명단 내보내기와 수신 동의 기록(047)까지만 있다. 실제 발송은 없다.
- **결정할 것**
  1. 발송 대행사(문자·알림톡 API 제공 업체)와 요금제. 후보 선정과 가격 비교는 아직 하지 않았다.
  2. 알림톡은 발신 프로필 등록과 **템플릿 사전 심사**가 필요한 것으로 알고 있다(업체별 절차 확인 필요). 일반 문자는 **발신번호 사전 등록**이 필요하다.
  3. 발송 비용을 누가 부담하는지(사업자 직접 계약 vs 플랫폼 일괄 계약)와 충전·정산 방식.
  4. 발송 시각 제한, 수신 거부 처리 방식(D-11).
- **설계 메모**: 발송 요청은 반드시 **API 서버를 거쳐** 하고 앱에 발송 키를 두지 않는다. 발송 이력 테이블(누가·언제·어느 고객·성공 여부)과 템플릿 저장, 실패 재시도가 필요하다. 이전 프로젝트(LCID)의 문자 템플릿 설계 문서(LCID 저장소 `docs/11`)를 참고할 수 있다.
- **권장**: 업체를 정하고 **테스트 발송 계정**을 받은 뒤 시작한다.

### D-02 네이버 예약 연동
- **조사 결과**: 공개된 네이버 예약 API 문서는 찾지 못했다. 연동 업체(핸드SOS, 테이블노트 등)는 제휴로 연동한 것으로 보이며, 제휴 문의가 가장 확실한 경로다. 크롤링·알림 메일 파싱은 약관 위반·차단 위험이 있어 운영 기능으로 권하지 않는다.
- **할 일(사용자)**: 네이버 개발자 센터에서 예약 관련 API 목록 확인 → 네이버 예약·스마트플레이스 제휴 문의(연동 목적, 예상 매장 수, 필요한 데이터 범위 정리).
- **대안**: 우리 앱의 자체 예약 링크(고객용 예약 페이지, 온라인 예약 APT-13). 앱이 아니라 웹 링크 방식이 비용이 낮다.
- **권장**: 제휴 문의를 먼저 보내고, 답을 기다리는 동안 자체 예약 페이지를 설계한다.

### D-03 SNS 홍보 도우미 (블로그·인스타·쇼츠·틱톡)
- **네이버 블로그**: 공식 글쓰기 API가 현재 쓸 수 있는지 확인하지 못했다(검색상 종료로 보이나 공식 근거 없음). 개발자 센터의 "공유하기"는 사용자가 직접 글쓰기 창을 여는 버튼으로 알고 있다. **권장안**: 앱이 글을 완성해 클립보드·ZIP으로 내보내고 블로그 글쓰기 창을 열어 주는 "도우미". 서식 있는 붙여넣기와 사진 붙여넣기가 스마트에디터에서 어디까지 되는지는 **직접 시험해야** 한다.
- **인스타그램**: 공식 콘텐츠 게시 API가 있다(프로페셔널 계정 필요, Meta 앱 검수 필요, 검수에 수 주 걸릴 수 있다는 자료가 있음, 24시간 게시 한도는 계정에서 확인). 이미지는 Meta 서버가 가져갈 **공개 URL**이 필요해 발행 순간에만 유효한 임시 URL이 필요하다. 토큰 갱신 주기와 권한 이름은 구현 전에 공식 문서로 확인한다.
- **유튜브 쇼츠·틱톡**: 업로드 API는 있는 것으로 알지만 앱 검수 전에는 비공개로만 게시되는 제한이 있다고 알고 있다. 영상 제작(사진 슬라이드 등) 범위까지 정해야 해서 개발량이 크다.
- **결정할 것**: 어느 채널을 먼저 할지, 동의된 사진만 쓸지, 영상까지 만들지.
- **설계 메모(차별점)**: 동의서에 "SNS 게시 동의" 항목을 두고 동의된 시술 사진만 후보로 보여 주며, 채널별 규격(1:1·4:5·9:16)과 캡션·해시태그 초안을 자동으로 만든다. 계정 토큰은 서버에 암호화해 보관한다.
- **권장 순서**: ① 동의서 SNS 동의 항목 → ② 블로그 도우미(복사·ZIP) → ③ 인스타 직접 게시(Meta 앱 검수를 일찍 시작) → ④ 쇼츠·틱톡은 사용 후 결정.

### D-06 카드 단말·PG·현금영수증·세금계산서 (SALE-12, FIN-11)
- 현재는 "실제로 받은 금액만 기록"하는 구조이고 카드 승인·이체를 실행하지 않는다. 카드 단말(PG) 연동, 현금영수증, 전자세금계산서는 각각 외부 사업자 계약과 인증이 필요하다. **결정**: 정말 필요한지(영수증 PDF로 충분한지), 필요하면 어느 사업자를 쓸지. 쿠폰·포인트는 외부 서비스 없이 가능하지만 정책(적립률, 유효기간, 환불 시 처리)을 먼저 정해야 한다.

### D-07 구성원 이메일 초대 (TEAM-12)
- 현재는 이미 가입한 사용자의 이메일로만 추가할 수 있다. 초대 메일은 서비스 키가 필요한 Supabase 초대 기능이나 별도 메일 발송 서비스가 필요하다. 서비스 키는 관리자 서버에만 있어야 한다는 원칙(SEC-02) 때문에 **관리자 API 경유 설계**가 필요하다. 구성원 추가 API의 시도 제한도 함께 정한다.

## 3. 배포·운영 준비 (사용자 작업)

### D-04 서버·도메인·설치본 배포
순서는 [배포 안내](../guide/admin/deployment.md)와 [릴리스 안내](../guide/admin/release.md)를 따른다.
1. API 서버를 둘 곳 결정(Oracle Cloud Always Free 또는 Lightsail 등)과 도메인, HTTPS 리버스 프록시.
2. 서버에 `apps/api` 빌드와 `.env` 배치(서비스 키는 관리자 서버 전용), 재시작 절차.
3. GitHub **Variables**: `BUSINESS_ASSISTANT_API_BASE`(필수, https), 선택 `BUSINESS_ASSISTANT_ADMIN_API_BASE`·`BUSINESS_ASSISTANT_STORAGE_HOST`·`TAURI_UPDATER_PUBKEY`. **Secrets**: `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)`(등록됨).
4. 첫 릴리스(`v0.x.x` 태그) 시험 설치와 자동 업데이트 확인.
5. 관리자 서버를 별도로 띄워 구독 메뉴 확인.

### D-05 코드 서명 인증서·업데이트
- 서명 인증서가 없으면 설치 시 Windows가 경고할 수 있다. 인증서 종류(일반/EV, 토큰 방식)와 구매처는 아직 정하지 않았다. 토큰 방식(HSM)을 쓰려면 `signCommand` 지원(OPS-04 잔여)이 필요하다. "서버 확인 자체 끄기" 옵션(Rust)도 잔여다.

### D-17 개발 PC의 Windows 앱 제어 정책
- 이 PC는 **스마트 앱 컨트롤**이 켜져 있어(레지스트리 값 1) 서명되지 않은 개발용 `.exe`가 실행되지 않는다(`os error 4551`). 그래서 지금까지의 화면 변경은 단위 테스트와 빌드로만 확인했고 **앱 창에서 직접 보지 못했다**. 선택지: 스마트 앱 컨트롤 끄기(한 번 끄면 Windows 초기화 전에는 다시 켜기 어려움), 다른 개발 PC 사용, 브라우저 웹 모드(`scripts/run-react-web.ps1`)로 확인(트레이·파일 선택 등 Tauri 기능 제외). 보안 설정은 사용자가 직접 바꾼다.

### D-18 실환경 검증 체크리스트
SQL은 격리 PostgreSQL(PGlite)에서 실행해 검증했지만 **실제 Supabase와 앱 화면에서의 확인은 아직**이다. 테스트 조직에서 아래를 손으로 확인하고 결과를 `backlog.md`에 `verified`와 날짜로 남긴다.
- 수납 → 매출 내역 반영, 지난달 **월 마감** 거절·재오픈(042).
- 서명 증빙 해시와 무결성 확인(043).
- 고객 **병합**(되돌릴 수 없음, 044), 태그 관리, 서버 검색.
- 구성원 추가·역할 변경·제거와 RPC 실행 권한(`anon` 없음, 045).
- 시술 소모품 차감과 재고 부족 롤백(046).
- 예약 메모, 할 일 라벨·체크리스트, 수신 동의 시각(047).
- 반복 할 일 생성, 고객 연결(048).
- 담당자 지정 → 담당 구성원이 완료 → "완료한 사람" 표시, 담당자가 다른 필드를 바꾸면 거절(049).
- 서비스별 담당 가능 직원: 지정한 직원만 예약 가능, 지정에서 빠진 직원의 기존 예약은 시간 변경·상태 변경 가능(050).
- 시술 프로토콜 템플릿 만들기·불러오기, 구성원은 읽기만(051).
- 시술 문서 서식에 새 자동 채움 항목(매장 이름·오늘 날짜·알레르기 등)을 넣어 미리보기·발행, 빈 값일 때 발행 차단, 발행 후 고객 정보를 바꿔도 발행본 고정(054).
- 사진 삭제 → 휴지통에서 삭제한 사람·시각 확인 → 복원, 구성원 화면에는 휴지통 없음(053).
- 반복 지출 등록(같은 달 재등록 시 중복 없음, 마감된 달 거절·재오픈 후 등록, 31일 말일 보정), 분류별·월별·세무용 내보내기 파일 열어 보기(052).
- 사진·파일 업로드·다운로드, 예약 끌어서 옮기기·충돌 거절, 감사 로그 조회(owner/admin).
- 영수증 PDF 저장, 글자 크기(1.25배)에서 레이아웃이 스크롤 없이 맞는지.
- Windows 설치본 빌드·설치·자동 업데이트.

## 4. 결정이 필요한 정책

### D-10 개인정보 보관·파기, 감사 로그 보관 (SEC-07, SEC-10)
- 현재 감사 로그는 **무기한 보관, 자동 파기 없음**이다. 고객 정보·사진·동의서의 보관 기간과 파기 방법(휴면 고객, 탈퇴 요청)은 정해지지 않았다.
- **결정할 것**: 항목별 보관 기간(감사 로그, 고객 정보, 시술 사진, 서명된 동의서), 자동 파기 여부, 조직별 설정 여부, DB 비용. 법정 보관 의무(전자상거래·회계 등)는 전문가 확인이 필요하다.
- 결정되기 전에는 파기 기능을 만들지 않는다.

### D-11 마케팅 수신 동의 운영 정책 (CRM-13)
- 현재는 고객별 동의 체크와 DB가 찍는 동의 시각만 있다. **동의 문구**, 동의 받는 방법(서면·구두·전자서명)과 증빙 보관, 철회 방법, 광고성 정보 전송 시간 제한(야간 발송), 수신 거부 안내 문구는 정해지지 않았다. 관련 법령(정보통신망법 등)은 최신 원문과 전문가 확인이 필요하다.
- 동의서(시술 동의서)와 별도로 둘지, 동의서 서식에 항목을 추가할지도 정한다.

### D-12 고객 병합 시 수신 동의
- 병합(044)은 **주 고객의 동의 값만 유지**하고 보조 고객의 동의는 합치지 않는다. "한쪽이라도 거부했으면 미동의" 같은 보수적 규칙을 둘지 결정한다.

### D-09 원가·인건비 반영 최종 손익과 수당 (LAB-10, TEAM-11)
- 경영 화면은 "관리손익 최종치가 아님" 경고를 유지한다. 최종 손익에는 **상품 원가(매입가)**, **직원 수당·인건비**, 세금 기록이 필요한데 앱에 데이터가 없다.
- **결정할 것**: 상품 원가를 입고 단가로 쓸지(평균법/선입선출), 서비스 원가는 소모품(046) 차감 기반으로 계산할지, 직원 수당 규칙(정률·구간·서비스별), 인건비 입력 방식. 수당 규칙은 TEAM-11과 함께 설계한다.

## 6. 이미 정해서 구현한 규칙 (바꾸려면 알려 주세요)
- **반복 할 일**: 기한이 있어야 하고, 완료하면 다음 회차가 자동 생성된다. 기한이 이미 지났으면 오늘 이후가 될 때까지 같은 간격으로 건너뛴다. 매월은 말일로 보정한다. 한 할 일의 다음 회차는 최대 1건이다.
- **할 일 담당자**: 담당자는 상태와 체크리스트만 바꿀 수 있고(제목·기한 등 불가), 완료한 사람은 DB가 기록한다. 담당자가 구성원에서 빠지면 다음 회차는 담당자 없이 만든다.
- **조회 전용 구성원**: 고객·할 일 등은 기본적으로 읽기만 가능하고, 자기에게 지정된 할 일만 완료할 수 있다.
- **홈 전월 비교**: 전월 같은 기간(말일 보정) 대비이며 기준이 0이면 비율을 보이지 않는다.

## 7. 이번 작업 중 발견해 고친 기존 결함 (참고)
- 할 일 상태·기한만 바꿔도 설명·우선순위가 덮어써지던 문제(수정 PATCH에 기본값이 적용). **이미 덮어써진 데이터는 복구할 수 없다.**
- 고객 프로필 저장이 읽기 전용 필드까지 보내 서버가 422로 거절하던 문제.
- 빌드에서만 드러난 import 누락(담당자 목록이 조용히 비는 문제). 목 API만 쓰는 테스트가 이런 결함을 가린 적이 있어, 실제 클라이언트를 쓰는 테스트를 보강하고 있다.
