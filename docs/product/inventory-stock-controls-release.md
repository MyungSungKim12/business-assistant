# 재고 반품·폐기·실사 조정 적용 안내

작성일: 2026-10-08 · 기능: INV-002 · 상태: 로컬 코드 검증 완료, 실환경 인수 전 `in-progress`

## 사용할 수 있는 흐름

매출·지출 → 결제 장바구니 → **상품 · 회원권 관리**에서 실물 상품을 선택한다. 거래처 반품, 폐기, 실사 조정을 선택하고 수량과 사유를 입력해 **재고 변동 기록**을 누른다.

- 거래처 반품과 폐기는 차감 수량을 입력한다. 현재 재고보다 많이 차감할 수 없다.
- 실사 조정은 실물로 확인한 총 수량을 입력한다. 현재 장부 수량과의 차이만 원장에 기록한다. 실사 후 다른 재고 변경이 먼저 일어나면 오래된 화면의 조정은 거부되므로 새로고침 후 다시 확인한다.
- 같은 요청을 다시 보내면 같은 결과를 반환한다. 원장 이벤트는 수정/삭제할 수 없다.
- 입고는 기존의 **선택 상품 입고** 흐름을 사용한다.

여기서 반품은 **거래처에 재고를 돌려보내는 처리**다. 고객 판매 상품의 부분 반품·환불은 이 흐름에 포함하지 않는다. 현재 SALE 환불은 결제 수납과 연계된 기존 전체 취소 복원 흐름까지 지원한다.

## DB 적용

Supabase SQL Editor에서 027~029가 적용된 대상 프로젝트를 확인한 뒤 [030_inventory_stock_controls.sql](https://github.com/MyungSungKim12/business-assistant/blob/main/migrations/030_inventory_stock_controls.sql)을 한 번 실행한다. 운영 DB에는 이 작업에서 적용하지 않았다. 적용 후 같은 버전의 서버와 데스크톱 앱을 재시작한다.

## 권한·복구 규칙

- owner/admin만 재고 변동을 기록할 수 있다. member는 상품과 허용된 원장을 읽을 수 있다.
- 조직 경계를 RPC에서 다시 검사하고, 직접 테이블 변경 권한은 열지 않는다.
- 요청 ID, 사용자, 요청 내용, 상품 버전을 함께 검사해 중복 실행·다른 내용 재사용·오래된 실사를 막는다.
- 응답이 불확실하면 앱이 보관한 동일 요청을 재시도한다. 새 요청으로 바꾸면 안 된다.

## 검증

- DB 격리 검증: 전체 `npm test` 통과. `scripts/db-tests/catalog-sales.mjs`의 9개 그룹에서 부분 거래처 반품, 폐기, 실사 조정, 재고 부족, 오래된 버전, 멱등성, 원장 불변, 역할/조직 경계, 마이그레이션 재실행을 확인했다.
- 서버/common 회귀 440개, 데스크톱 회귀 230개 통과. Ruff 전체 검사와 변경 파일 형식 검사, 변경한 네 Python 파일의 mypy, MkDocs strict 빌드 통과.
- PGlite 검증은 실제 Supabase의 다중 연결 경합·RLS 운영 설정·실계정 사용을 대신하지 않는다. 실제 Windows 화면 인수와 고객 판매 상품 부분 환불은 남아 있다.

커밋·푸시·배포·운영 데이터 변경은 수행하지 않았다.
