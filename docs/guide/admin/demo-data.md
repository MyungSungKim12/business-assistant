# 데모 데이터 만들기

기초 데이터가 없는 개발·시험 환경에서 기능별로 약 10건씩 연습용 데이터를 만드는 스크립트입니다. 실제 고객이나 금액이 아니며, 이름에 `[데모]`가 붙고 전화번호는 `010-0000-xxxx`, 이메일은 `@example.com`입니다.

!!! danger "운영 DB에는 넣지 마세요"
    이 스크립트는 고객·매출·수납·재고·마감 같은 **되돌리기 어려운 데이터**를 만듭니다. 매출 원장과 재고 이력은 수정·삭제할 수 없게 설계되어 있습니다. 반드시 시험용 매장(조직)이 있는 개발·시험 프로젝트에만 사용하고, 실제 매장이 쓰는 운영 서버에는 실행하지 마세요.

## 동작 방식

스크립트는 SQL을 직접 넣지 않고 **Node API(`apps/api`)를 HTTP로 호출**합니다. 그래서 재고, 버전 잠금, 멱등 키, 예약 충돌 같은 규칙이 화면에서 쓰는 경로와 똑같이 지켜집니다.

- 먼저 `[데모]` 표식이 있는 기존 데이터를 조회해서 이미 있으면 건너뜁니다. 여러 번 실행해도 중복이 생기지 않습니다.
- 서버 멱등이 필요한 쓰기에는 매장과 항목 이름으로 만든 고정 `operation_id`를 사용합니다.
- 한 영역이 실패해도(구독에 없는 기능, 적용하지 않은 SQL 등) 다른 영역은 계속 진행하고, 마지막에 영역별 성공·건너뜀·실패 요약표를 출력합니다. 실패 원인은 HTTP 상태와 서버가 돌려준 `detail`만 보여주며, 비밀번호나 토큰은 출력하지 않습니다.
- 요청 사이에 50ms 간격을 두고, 조회와 `operation_id`가 있는 쓰기는 5xx·네트워크 오류 때 같은 키로 최대 2회 다시 보냅니다. 키가 없는 생성 요청(고객·할 일·문서·수입지출 등)은 중복을 막기 위해 다시 보내지 않으므로, 실패하면 다시 실행해 이어서 만듭니다.

## 사전 조건

1. Node API 서버가 실행 중이어야 합니다. 기본 주소는 `http://127.0.0.1:8000/api/v1`입니다. (`scripts/run-server.ps1`)
2. 데이터베이스에 마이그레이션이 **039번까지** 적용되어 있어야 합니다. 앞쪽 일부만 적용된 DB에서는 해당 영역이 실패하거나 건너뛰어집니다.
3. 대상 매장에서 **owner 또는 admin**인 계정이 필요합니다. 구독에 필요한 기능(`crm.basic`, `task.basic`, `finance.basic`, `document.template`, `files.basic`)이 없으면 그 영역은 건너뜁니다.
4. 계정은 환경변수로 전달합니다. 명령줄 인자로 비밀번호를 받지 않습니다.

| 환경변수 | 설명 |
| --- | --- |
| `SEED_EMAIL`, `SEED_PASSWORD` | 우선 사용하는 계정 |
| `BUSINESS_ASSISTANT_DEV_EMAIL`, `BUSINESS_ASSISTANT_DEV_PASSWORD` | `SEED_*`가 없을 때 쓰는 개발용 계정 |
| `APP_API_BASE_URL` | API 주소(서버 주소만 있으면 `/api/v1`을 자동으로 붙입니다) |

저장소 루트의 `.env`가 있으면 위 키만 읽습니다(`--env-file <경로>`로 다른 파일 지정). 이미 설정된 환경변수가 우선하며, 값은 화면이나 로그에 출력하지 않습니다.

## 실행 방법

PowerShell에서 저장소 루트로 이동해 실행합니다.

```powershell
# 1) 계획만 확인(네트워크 요청 없음)
node scripts/seed-demo-data.mjs --dry-run

# 2) 계정 설정 후 실행(대상 주소·매장·마스킹된 이메일을 보여주고 확인을 묻습니다)
$env:SEED_EMAIL = "<시험 계정 이메일>"
$env:SEED_PASSWORD = "<시험 계정 비밀번호>"
node scripts/seed-demo-data.mjs --org test

# 3) 일부 영역만(선행 영역은 자동 포함)
node scripts/seed-demo-data.mjs --org test --only customers,tasks --yes
```

종료 코드는 `0` 성공(건너뜀 포함), `1` 일부 영역 실패, `2` 옵션·안전장치·로그인 오류입니다.

### 옵션

| 옵션 | 설명 |
| --- | --- |
| `--org <slug>` | 대상 매장 slug(기본 `test`). 역할이 owner/admin이 아니면 중단합니다. |
| `--api <url>` | API 주소(기본 `http://127.0.0.1:8000/api/v1`). |
| `--allow-remote` | 로컬(127.0.0.1·localhost)이 아닌 주소를 허용합니다. 로컬이 아니면서 https가 아닌 주소는 이 옵션이 있어도 거부합니다. |
| `--yes`, `-y` | 실행 전 확인 질문을 생략합니다. |
| `--dry-run` | 요청을 보내지 않고 영역별 생성 예정 개수만 출력합니다. |
| `--only <영역,...>` | 일부 영역만 실행합니다. `--help`에서 영역 키와 선행 관계를 볼 수 있습니다. |
| `--env-file <경로>` | `.env` 위치를 지정합니다. |
| `--delay-ms <숫자>` | 요청 사이 간격(기본 50). |

## 만들어지는 데이터

| 영역 키 | 만들어지는 데이터 | 개수 | 선행 영역 |
| --- | --- | --- | --- |
| `customers` | 고객(태그·피부타입·방문일 다양) | 10 | - |
| `tasks` | 할 일(열림·진행·완료·취소, 우선순위 다양) | 10 | - |
| `staff` | 예약 담당자, 요일별 근무시간(월–토), 휴무 | 10 / 10 / 3 | - |
| `services` | 예약 서비스(시간·버퍼 다양) | 10 | - |
| `resources` | 예약 공간 5, 장비 5 | 10 | - |
| `requirements` | 서비스별 필수 자원 기준(공간, 일부는 장비 추가) | 10 | services, resources |
| `appointments` | 예약(자원 선택, 확정·방문·완료·노쇼·취소 사유) | 10 | customers, staff, services, resources, requirements |
| `treatments` | 시술 기록(초안·상담·진행·완료·중단) | 10 | customers |
| `saleDrafts` | 시술 판매 초안(완료 5, 중단 1) | 6 | customers, treatments |
| `products` | 제품 7, 회원권·패키지 3 | 10 | - |
| `inventory` | 입고 7건, 재고 조정(폐기·실사·반품) 3건 | 10 | products |
| `sales` | 방문·장바구니 8흐름: 복합 수납, 할인, 일부 환불, 제품 판매와 반품(재입고), 회원권 판매→지갑 생성, 지갑 금액·횟수 사용, 미수 | 8 | customers, treatments, saleDrafts, products, inventory |
| `closing` | 일 마감 1건(오늘이 아닌 과거 영업일, 3일 전) | 1 | - |
| `finance` | 수입 4·지출 6(최근 30일, 카테고리 다양) | 10 | - |
| `templates` | 문서 서식 4개(3개 발행, 1개 초안) | 4 | - |
| `documents` | 문서(초안·확정·보관) | 10 | templates |
| `consents` | 시술 문서 발행 3, 동의서 서명 2, 교부 1(서명은 작은 합성 획) | 3 | customers, treatments, templates |
| `files` | 파일 자료(작은 txt/csv, 서명 업로드 URL로 전송) | 10 | - |

### 만들지 않거나 건너뛰는 항목

- **관리 미리보기**는 다른 데이터에서 계산되는 값이라 따로 만들지 않습니다.
- **일 마감은 오늘 날짜로 하지 않습니다.** 수납은 항상 오늘 영업일로 기록되고 마감된 날에는 수납할 수 없으므로, 3일 전 영업일을 마감합니다. 그 날짜에 실제 수납이 있으면 시재(현금)를 계산된 예상 현금으로 입력합니다.
- 예약은 담당자 근무시간(월–토 10:00 이후)과 휴무를 피해, 날짜가 겹치지 않게 오늘 기준 -5일~+5일에 배치합니다. 일요일은 피합니다.
- 방문 흐름은 같은 고객의 n번째 방문이 이미 완료 상태면 건너뜁니다. 흐름 중간에 중단되었다면 같은 `operation_id`로 이어서 진행합니다.
- 고객 활동·고객 사진·시술 사진은 만들지 않습니다.
- 구독에 기능이 없으면(403, `feature_code`) 영역을 건너뛰고, 그 영역에 의존하는 영역도 함께 건너뜁니다.
- 날짜가 필요한 데이터는 실행한 날을 기준으로 계산됩니다. 다른 날 다시 실행해도 `[데모]` 이름·SKU·메모로 기존 데이터를 찾아 중복을 만들지 않습니다.

## 지우는 방법

삭제 스크립트는 제공하지 않습니다. `[데모]` 표식이 있는 데이터는 **앱에서 보관하거나 삭제**하세요(고객은 보관, 할 일·문서·파일 자료는 화면 기능 사용).

매출·수납·재고 원장은 변경·삭제가 막혀 있고 다른 기록이 참조하므로, 판매·수납까지 만든 시험 조직은 새 시험 조직을 만들어 쓰는 편이 안전합니다. 영구 삭제가 꼭 필요한 경우를 위한 **참고용** SQL 예시입니다. 이 문서에서는 실행하지 않았으며, 시험 프로젝트에서 조직 ID를 바꿔 확인한 뒤 SQL Editor에서 직접 실행하세요. 참조하는 기록이 있으면 오류가 나고, 그 경우 해당 데이터는 지울 수 없습니다.

```sql
-- 참고용 예시(실행하지 않음). 반드시 시험 프로젝트에서만, 조직 ID를 확인하고 사용하세요.
begin;
-- 먼저 지울 대상을 확인합니다.
select count(*) from public.tasks where organization_id = '<시험 조직 ID>' and title like '[데모]%';
-- 참조 관계가 없는 단순 데이터만 예시로 지웁니다.
delete from public.tasks where organization_id = '<시험 조직 ID>' and title like '[데모]%';
delete from public.documents where organization_id = '<시험 조직 ID>' and title like '[데모]%';
delete from public.finance_transactions
 where organization_id = '<시험 조직 ID>' and memo like '[데모]%';
-- 결과를 확인한 뒤 의도한 대로이면 commit, 아니면 rollback 하세요.
rollback;
```

## 확인 목록

- `--dry-run`으로 영역별 예정 개수를 먼저 확인했는가
- 대상 주소가 로컬 또는 시험용 서버인가(요약 화면의 API 주소와 매장 이름 확인)
- 계정이 시험 매장의 owner/admin인가
- 운영 DB·실제 매장에 실행하지 않았는가
