# 문제 해결

증상과 상태 코드를 먼저 확인하고 아래 순서대로 처리합니다. 금액·재고 변경 작업은 결과를 확인하기 전에 반복하지 않습니다.

## 서버가 실행되지 않음

### `_ssl` DLL이 애플리케이션 제어 정책에 차단됨

이 오류는 실행 명령이 틀린 것이 아니라 회사 PC 보안 정책이 `uv`가 설치한 Python의 `_ssl.pyd` 또는 관련 DLL 로드를 막은 경우입니다.

1. `scripts/run-server.ps1`이 실제로 사용하는 Python 경로를 확인합니다.
2. 회사에서 허용한 Python 배포판 또는 승인된 설치 경로를 사용합니다.
3. 보안 담당자에게 차단된 파일 경로와 오류 시각을 전달해 허용 정책을 요청합니다.
4. 임의로 보안 프로그램을 끄거나 DLL을 인터넷에서 내려받아 교체하지 않습니다.

이 문제가 있는 PC에서도 소스 편집은 가능하지만 서버와 앱의 실동작 검증은 허용된 다른 로컬 환경에서 수행해야 합니다.

### `서버 실행에 실패했습니다`

이 문구 바로 위의 최초 Python 오류가 실제 원인입니다. 포트 충돌이면 8000번 포트를 사용 중인 프로세스를 확인하고, 설정 오류면 `.env`의 필수 값을 확인합니다.

## 로그인 401과 `getaddrinfo failed`

Supabase 프로젝트가 일시 중지되었거나 `APP_SUPABASE_URL`의 호스트 이름을 찾지 못한 상태입니다.

1. Supabase Dashboard에서 프로젝트가 활성 상태인지 확인합니다.
2. `.env`의 URL에 오타·공백이 없는지 확인합니다.
3. 회사 DNS·프록시에서 Supabase 도메인 접근이 가능한지 확인합니다.
4. 서버를 재시작한 뒤 로그인합니다.

## 403 Forbidden

로그인은 됐지만 조직 역할 또는 기능 권한이 없는 요청입니다. 현재 조직, 멤버십 역할, 활성 구독과 기능 코드를 확인합니다. 화면 버튼을 강제로 활성화하는 방식으로 해결하지 않습니다.

## 사진 등록·조회가 400 또는 503으로 실패함

### `InvalidKey`

과거 사진의 Storage 경로에 허용되지 않는 문자가 포함된 경우입니다. 최신 서버는 새 업로드 이름을 안전하게 변환합니다. 기존 잘못된 메타데이터는 원본 보존과 실제 Storage 객체를 확인한 뒤 관리 절차로 정리합니다.

### upload-url 또는 download-url 503

1. `APP_SUPABASE_URL`, `APP_SUPABASE_SERVICE_KEY`, `APP_FILE_BUCKET`을 확인합니다.
2. 022와 023 마이그레이션이 적용됐는지 확인합니다.
3. Supabase Storage에 설정한 비공개 버킷 이름이 `.env`와 같은지 확인합니다.
4. 서버 로그의 `Supabase storage request failed` 바로 뒤 상태와 본문을 확인합니다.
5. 설정을 바꿨다면 서버를 재시작합니다.

## 고객을 누를 때 느림

고객 선택 시 기본 정보 외에 상담 활동과 사진 목록·서명 URL을 함께 요청하면 네트워크 지연이 누적될 수 있습니다. 최신 화면은 기본 정보와 필요한 탭 데이터를 나눠 불러옵니다. 계속 느리다면 실패한 사진 URL 요청이 반복되는지, Supabase 지역과 네트워크 지연이 큰지 확인합니다.

## 수납·입고·환불 결과를 알 수 없음

화면에 저장된 복구 버튼을 사용합니다.

- **같은 요청 재시도**
- **미확인 수납 다시 확인**
- **미확인 사용 다시 확인**
- **미확인 환불 다시 확인**

복구 결과가 확정되기 전에는 새 요청을 만들지 않습니다. 자세한 순서는 [환불·취소·미확인 복구](workflows/refunds-and-recovery.md)를 확인합니다.

## 문서 사이트가 열리지 않음

- 앱 서버와 문서 서버가 모두 8000번 포트를 사용하면 문서를 8001번으로 실행합니다.
- GitHub Pages에서 404가 나면 저장소 Pages Source가 GitHub Actions인지 확인합니다.
- 배포 Action이 실패하면 `mkdocs build --strict` 로그의 첫 경고부터 수정합니다.
